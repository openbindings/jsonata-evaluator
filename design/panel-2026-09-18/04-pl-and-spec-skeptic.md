# Panel cold read: pl and spec skeptic

> 2026-09-18. Given only the class README and the vetted API stub; told not to read anything else. Verbatim.

## Attacking the concept

### 1. Documentation as authority

**The attack.** The JSONata documentation is tutorial prose and a function reference, written after the fact by the same author to describe the reference implementation. It is not a specification: it has no grammar with precedence tables, no evaluation-order rules, no definition of the value domain, no statement of what a number is, no enumeration of error conditions, and it is silent on most of the sequence/singleton-unwrapping corner cases that make JSONata JSONata. Declaring such a text "the authority" does not make it one; it moves the authority into whoever reads it. When two engineers disagree about what a passage means, the README offers no tie-breaker. When the documentation contradicts itself (it describes the same behavior in the tutorial pages and the function reference with different wording, and those pages drift), there is no rule for which page wins.

Worse, the README's own gate contradicts the stance. Rule 1 verifies members "against the reference test suite." Rule 6 permits departing from that suite "only where the value model cannot represent a reference value." The suite encodes what the reference *does*, including every place the reference departs from its documentation. So on the README's own terms: where documentation and fixture disagree, the member must match the fixture, because "the docs said otherwise" is not a permitted divergence category. The stated authority (documentation) is overruled by the operational authority (suite) every time they conflict. Concrete instance I am fairly confident about: the reference's `$string` rounds numbers to 15 significant digits before formatting (a `toPrecision(15)` in the stringify path), so `$string(0.1 + 0.2)` is `"0.3"` in the reference. If the pinned documentation does not state that rounding, a Go member using `strconv` yields `"0.30000000000000004"`, the suite almost certainly has fixtures exercising it, and rule 6 does not permit the divergence. The README's flagship example, "`0.1 + 0.2` is whatever the host yields," collides with its own gate the moment the value is stringified.

There is also a causality problem. Documentation describing an implementation is downstream of that implementation. When they disagree, the prior that the docs are stale is at least as strong as the prior that the code is wrong; the JSONata maintainers fix docs to match code routinely. Pinning the docs at a commit freezes documentation bugs as language law with no appeal.

**Steelman.** Every other port copies the reference's bugs. Choosing the docs at least gives a text that can be argued about in public, that does not change when someone refactors `functions.js`, and that a second implementer can read without reverse-engineering JavaScript. OpenBindings Core already pins docs-at-a-commit, so the class is following its consumer.

**Does it land?** Yes, as stated. Not because docs-as-authority is worthless, but because the README claims a single authority while operating a hybrid one (documentation where it speaks and is consistent with the suite; suite everywhere else) and does not say so. An authority that cannot adjudicate its own conflicts is not an authority; it is a preference. The fix is to name the hybrid honestly and give the divergence ledger the categories it needs (see "What I would change").

### 2. Host-native value model

**The attack.** The library's job is per-value transforms in interface documents that ship to unknown clients. The README says outright that two members "differ, and that is correct" where their value models differ. Read that as a PL statement: the denotation of a transform is not a function of (expression, input); it is a function of (expression, input, evaluator). An interface author writing `$$.id + 1` on a 64-bit identifier gets an exact result in Go, a wrong result in a JavaScript member, and there is no rule in the class requiring either member to tell them. "The portable core" is offered as an observation, which is exactly backwards: the part everyone agrees on is what needs to be a rule; the host-specific tail is what should be an observation.

The "silence" premise is also doing more work than it can bear. The README asserts "the documentation never says what a number is." I cannot verify the pinned docs from this cold read, but I would want that claim cited to a passage before it carries the whole numeric model; I believe the docs name JSON's number type and discuss double-precision behavior in at least one place. If the docs say numbers are IEEE doubles anywhere, "documentation wins where it speaks" hands the numeric model back to binary64 and the host-native integer model becomes an undeclared divergence.

Within a single host, the model as written is not even self-consistent. "Any float64 operand yields float64" applied to `*big.Int + float64` converts a big integer to a double, which is an approximation; rule 8 says the member "refuses rather than approximates." "Integer with integer stays integer" does not say which integer: `uint64(1) + int64(-2)` has no home in either named result type. `int8 + int8` either overflows at 127 (absurd) or promotes (then say so). `float32` is admitted but never mentioned in the combination rules.

**Steelman.** The evaluator cannot be more faithful than its host's decoded values. A JS consumer has already lost the 64-bit ID before any expression runs; forcing the Go member to compute in binary64 would throw away exactness the host has, to match a host that does not. "Owes no more than its host offers and must not offer less" is a coherent principle for a local tool, and the boundary is already host-native by the time values arrive.

**Does it land?** It lands for the portable use case and misses for the local one. The principled resolution is not "one model everywhere" and not "each host its own"; it is *agreement or refusal*: for any expression and input, two members either return equal values or at least one refuses. That keeps the Go member's exactness, forces the JS member to refuse `$$.id + 1` beyond 2^53 rather than round, and makes cross-host disagreement impossible rather than "correct." Rule 8 is two words away from saying this already.

### 3. The regex analogy

**The attack.** The analogy borrows the confidence of formal language theory for a language that has none. Regex notation has a mathematical semantics underneath (regular languages); engines diverge only in extensions (backreferences, lookaround, Unicode classes), and RE2's whole reason to exist was to pin a dialect to that math. JSONata's "notation" has no math under it; the notation *is* the reference implementation's behavior. Porting the analogy imports the shape of the argument and none of its ground.

The analogy also picks the wrong precedent from its own domain. Regex engines fragmented into incompatible dialects, and where regexes were embedded in cross-system contracts, the response was to *pin a dialect*: OpenAPI's `pattern` is nominally ECMA-262 precisely because "each host does its own" produced schemas that validated differently per client. Transforms in interface documents are that case exactly. The regex world's lesson for this situation is the opposite of what the README draws from it. And "nobody ports PCRE to Go" is false: `regexp2` exists because people needed .NET-compatible semantics and RE2's dialect would not do. Reference-faithful ports are what the market demanded when semantics had to match across systems.

**Steelman.** The analogy is meant to license one specific thing: not serializing to JSON text or an intermediate tree, and treating host strings and numbers as the host's. On that narrow point it is apt; Go's `regexp` really does operate on Go strings and rune semantics without pretending to be a JS engine.

**Does it land?** Yes. The analogy is decorative for the semantic claim and load-bearing only for the implementation claim (by-reference, no intermediate tree). Keep the second, drop the first, and stop citing regex engines as evidence that per-host divergence is fine; they are the evidence that it is not.

### 4. Declared divergence as sufficient discipline

**The attack.** The ledger only records what the suite detects, and the suite tests the reference, not the documentation. Three classes of drift are invisible to it: (a) places where the reference departs from the documentation and the member faithfully copies the reference to pass the fixture; (b) places where the documentation is silent, the suite has no fixture, and the member made a choice nobody wrote down; (c) places where two members made different silent choices and both pass. Rule 6's single permitted reason (unrepresentability) cannot even express the situation the README says is fundamental (documentation contradicts reference). A ledger with one category and one gate is not a discipline; it is a changelog.

Pinning declarations to fixtures is a good mechanism, but a fixture change invalidating a declaration is only meaningful if someone is obligated to re-derive it; the README does not say what happens then.

**Steelman.** A pinned, per-fixture, reasoned ledger is more discipline than any existing JSONata port has, and it is checkable by a third party.

**Does it land?** Partly. The mechanism is right; the taxonomy is too small and the gate is mis-stated. Three categories (unrepresentable; fixture contradicts documentation, with the passage cited at the pinned docs commit; documentation silent, value model chose) and a requirement that silent-choice declarations be shared across project members would make it a discipline.

### 5. Choosing JSONata at all

**The attack.** CEL has a written specification, a static type checker, non-Turing-complete evaluation with cost estimation, and a conformance suite run by several independent implementations. JMESPath has an ABNF grammar, a spec, a JEP process, and a compliance suite. JSONata has a JS program and prose. The README's own "portable core" is object and array literals, variable bindings, conditionals, comparisons, and a dozen functions; that subset is expressible in CEL today with a spec behind it. Meanwhile the full language brings lambdas, recursion, regex, and higher-order functions, which is why the API needs `WithMaxRecursion`, `WithMaxOutputNodes`, and budget refusals at all. The project chose a language whose power it does not use and whose specification it does not have, then built a class to compensate for the missing specification.

**Steelman.** JSONata is a *transformation* language: object construction with grouping, array reshaping, and path navigation are first-class and read naturally. CEL is an expression language that constructs poorly; JMESPath has no arithmetic worth the name and no object construction beyond multiselect. The transform's job is reshaping, and JSONata is the best-known notation for that job. Ecosystem adoption (Node-RED and friends) means authors already know it.

**Does it land?** As a "should have been CEL" argument, no; the reshaping ergonomics are real and the portable core is exactly the reshaping subset. As a "the class is the wrong lever" argument, yes: the deficiency is a missing specification for a small subset, and the fix for that is to write the specification for the subset, not to redefine authority for the whole language.

## What a PL person would want instead

Ranked by value per effort, highest first.

1. **A normative profile for the portable core, pinned by OpenBindings Core.** Turn the "observation" into a rule: the constructs and functions listed, a precise (prose-level, but exhaustive) semantics for each, and a stated numeric domain. Two to four pages. This is what interface authors actually need and it is the part where docs and reference already agree, so it costs nothing in divergence.

2. **A numeric model stated as agreement-or-refusal.** Define the portable numeric domain (integers exact within the signed 53-bit range, otherwise binary64), define the value function `V` from every admitted representation to that domain, require every observing operation to be a function of `V`, and require a member whose host cannot compute a result exactly within its stated model to refuse. This single change removes the cross-host disagreement the README currently calls "correct" while keeping the Go member's exactness.

3. **Reference-fixed semantics as the declared fallback.** Say plainly: the documentation governs where it speaks and is consistent with the suite; the pinned reference suite governs where the documentation is silent; the ledger records every place either one is overridden. This costs one paragraph and makes the stance coherent. It is what the class already does; it just does not admit it.

4. **A small-step semantics for sequences.** The notorious part of JSONata is sequence flattening, singleton unwrapping, and undefined propagation through paths, predicates, and constructors. Prose will never settle it. An operational semantics for paths plus the constructors, perhaps two pages of rules, would settle every "what does `a.b[0]` mean when `b` is a singleton array" argument forever and would make the profile in (1) actually checkable. Moderate effort, high durable value.

5. **A typed pairing.** Interface documents already carry JSON Schema for the values a transform reads and produces. A checker that types a profile expression against the input schema and verifies it against the output schema catches most authoring errors at document-validation time and is the CEL move that JSONata never got. High effort; do it after (1) and (2).

6. **A different language.** Not now. The reshaping ergonomics are the reason JSONata was picked and the alternatives do not have them.

## Semantic commitments hidden in the API

**Absence as `(value, present, err)`.** Sound at the top level, and better than a sentinel. Undefined: what `present` means when `err != nil`; whether `Access.Get` returning `ok == false` is absence or null (the doc implies absence, but say it); and, in `text.Evaluate`, "no bytes with nil error" makes an absent result indistinguishable from a bug that returned an empty slice, and is not a JSON text, so any caller piping the output into a decoder fails. `text.Evaluate` should return `([]byte, bool, error)` for symmetry with the native API.

**`*Object` for constructed objects, `map[string]any` admitted as input.** The commitment is that output object type depends on whether the expression constructed or carried: `$$` returns the caller's map, `$merge([$$, {}])` returns `*Object`. That is a consequence of exact carriage and is defensible, but it should be stated in the package doc so callers do not type-assert on one and crash on the other. The doc says insertion order is "as the language requires." I doubt the documentation requires it; the reference *behaves* as JavaScript objects behave, which orders integer-like keys numerically before string keys in insertion order. `$keys({"b": 1, "10": 2, "2": 3})` yields `["2", "10", "b"]` in the reference and `["b", "10", "2"]` under this API's `Object`. If a fixture covers it, the member fails rule 6, since the divergence is not about representability. Either match the reference's ordering, or declare the divergence in a category rule 6 does not yet have. Also undefined: what order `$keys`, `$each`, and `$spread` see on a `map[string]any` input, which has no order at all; nondeterministic iteration would violate rule 9 and every reasonable expectation. Say "sorted" or say "insertion order is unavailable for maps and functions that observe order treat map keys as sorted."

**The admitted numeric zoo.** Sixteen numeric input types with one paragraph of combination rules. Undefined: the result integer type (int64? uint64? the wider operand?); mixed-sign operands (`uint64 + int64`); whether narrow types promote or overflow at their own width (the `CodeOverflow` comment says int64 or uint64, so promotion is intended, but the package doc does not say); `float32` anywhere; `*big.Int + float64`, which as written approximates and thereby violates rule 8; and non-finite *inputs*, which Go values can carry and JSON cannot (rule 8 speaks only of results). Recommendation: admit everything, but define exactly three result types (`int64`, `float64`, `*big.Int`), promote all narrow integers and `float32` at admission, convert `uint64` above `MaxInt64` to `*big.Int`, and make `*big.Int` with a float operand a refusal unless the big value is exactly representable as float64.

**Numbers "returned as carried" versus computed.** Sound for pure copy, and it is what makes the `text` package round-trip `1.0` as `1.0`. Unsound the moment a carried representation is *observed*: `$string(json.Number("1.0"))` yielding `"1.0"` while `$string(1.0)` yields `"1"` means a grouping key or a `$string`-built identifier depends on the input's textual token, which the reference collapses to `"1"` for both. Rule 4 says "same numeric value," which is weaker than "same token" and is the right strength; the API doc should say that carriage preserves the representation but every function of the value sees `V(x)`, never the token.

**Comparison "by value across representations."** Taken literally this is a landmine. `json.Number("0.1")` is mathematically one tenth; `float64(0.1)` is not. Under a literal reading `x = x * 1` is false for `x = json.Number("0.1")`, because `x * 1` went through float64. Under the loose reading (convert both to float64), `json.Number("0.1000000000000000055511151231257827")` equals `0.1`, which is fine but must be said. The rule needs a defined comparison domain and a defined `V`; the sane choice is `V(json.Number) = int64` when the token is integral and in range, else the nearest float64, and equality in the domain of exact rationals over `{int64, float64, *big.Int}` (which is decidable and cheap). Also undefined: which representation survives `$distinct([1, 1.0, json.Number("1.00")])`, and stability of `$sort` among values equal under `V` but distinct as representations.

**`Access.Number(v any) any` "exactly."** For a protobuf `double` or `int32` this is fine. For a decimal or money type, "exactly" is impossible in any admitted type except `json.Number`, so `json.Number` is silently the exact-decimal carrier for the whole API and the doc should say so. `Number` has no failure return: an implementation that cannot produce an exact admitted value has nowhere to go but panic. Make it `(any, error)` or `(any, bool)`. `Access.Keys` promises "in order"; `Kind` does not distinguish "unset optional field" from null, which for protobuf is the whole question; the doc should state that `Get` returning `ok == false` is absence.

**`Reads() ([]string, bool)`.** "Top-level input paths" as strings, with no stated encoding. Keys containing dots or slashes make a dotted or slashed encoding ambiguous. Say JSON Pointer, or return `[][]string`.

**Selective evaluation "when the subexpression is pure."** JSONata has no side effects, so "pure" here can only mean "cannot fail or exhaust a budget," and the doc does not say that. Rule 9 ("identical to the same field of a complete evaluation") is vacuous when the complete evaluation fails: `{"a": 1, "b": $error("x")}` has no complete result to be identical to, and `Select("a")` returning `1` is either a feature or a rule violation depending on wording nobody wrote. Similarly `WithMaxOutputNodes` can be satisfied selectively and exceeded completely. State it: "when Complete would succeed, Select yields the same field; when Complete would fail, Select may succeed for fields that do not depend on the failing subexpression." Also: duplicate literal keys in a constructor are an error in the language (D1009); `Select("a")` on `{"a": 1, "a": 2}` must error, not return `1`.

**`Error.Code` "where the documentation defines one."** If the S/T/D codes are enumerated only in the reference source and not on any pinned documentation page, the error surface is already reference-defined, and the API doc should say "the reference's code" rather than "the documentation's." Worth checking before it ships in a doc comment.

**Package doc: "JSONata 2.1."** The consumer pins documentation at a commit. The package should export that commit (`const DocumentationCommit = "..."`), so a caller can verify the member and the interface document agree on which language they mean.

## What I would change

1. **Replace "No parity between members" with agreement-or-refusal, and widen rule 8 to cover precision loss.** README rule 8: "It refuses rather than approximates. Overflow, non-finite results, exhausted budgets, unrepresentable values, *and any arithmetic or conversion whose result is not exact in the member's stated model* are failures, never rounded, saturated, or coerced." README "What membership does not require": strike "No parity between members" and add under membership: "**Members agree or refuse.** For any expression and input, two members return equal values under rule 5, or at least one refuses." This is the change that makes host-native values compatible with cross-system transforms.

2. **Promote the portable core from observation to a normative profile, with a numeric domain.** README: "**The portable profile.** The following constructs and functions are the OpenBindings transform profile: [list]. The profile's numeric domain is integers exact within ±2^53 and binary64 otherwise. Every member computes the profile identically; the project pins the profile in Core." Then keep the full language as the extension a member may offer.

3. **Define the value function and make observation a function of it.** Package doc, replacing the "Numbers combine" paragraph: "Every admitted numeric representation has one numeric value: for int8 through int64 and uint8 through uint32, the integer; for uint64, the integer, held as *big.Int above MaxInt64; for float32 and float64, the binary64 value; for *big.Int, the integer; for json.Number, the int64 the token denotes when integral and in range, otherwise the nearest binary64. Arithmetic, comparison, ordering, membership, $type, $string, and object keys are functions of that value, never of the representation. A value the expression only copies keeps its representation. Results are int64, float64, or *big.Int: integer with integer is int64, or *big.Int when either operand is big; any float operand yields float64; *big.Int with a float operand is a refusal unless the big value is exactly representable as float64. "/" is int64 when exact, float64 otherwise." And `Access.Number(v any) (any, error)`.

4. **Give the divergence ledger the categories the stance needs, and state the hybrid authority.** README rule 6: "A departure from the reference suite is permitted only in three declared forms: (a) the value model cannot represent a reference value; (b) the fixture contradicts the pinned documentation, citing the passage at the pinned commit; (c) the documentation is silent and the fixture encodes a reference choice the value model does not make. Each declaration is pinned to the fixture; a fixture change invalidates it and the member fails until it is re-derived. Declarations of form (c) are shared across the project's members." And in "The split": "Where the documentation is silent, the reference suite governs unless a declaration of form (c) says otherwise."

5. **Fix the `Object` order claim and the map-order gap.** `Object` doc: "Object is an insertion-ordered object: the type of every object the expression constructs." Strike "as the language requires." Add to package doc: "The reference orders integer-like keys numerically before other keys; this member preserves insertion order and declares the divergence (ledger entry N)." Or match the reference; either is defensible, silence is not. And: "Functions that observe member order on a map[string]any input see keys in sorted order." Secondary, same change: `text.Evaluate` returns `([]byte, bool, error)`.

## On the concept

This is a well-argued position that is wrong in one specific and repairable way. The engineering stance, by-reference host values, no intermediate tree, a pinned suite, a ledger of declared divergences, selective evaluation constrained to be unobservable, is better discipline than any existing JSONata implementation has, and I would want every member of the class to be built this way. The trouble is the semantic stance layered on top. "Documentation as authority" names an authority that cannot adjudicate, and the README's own gate quietly substitutes the reference suite wherever the documentation is silent or disagrees, without a divergence category that can even describe the substitution. The stance is a hybrid pretending to be a monarchy. Say what it actually is and it becomes coherent overnight.

The host-native value model is principled for a local tool and an abdication for this tool. A transform in an interface document is a program whose meaning must be a function of the program and its input, not of which client happens to evaluate it. The README not only permits members to disagree, it calls the disagreement correct, and offers the "portable core" as an observation rather than a promise. The regex analogy does not rescue this; regex is the domain where per-host dialects were tried, fragmented, and had to be pinned back the moment patterns were embedded in cross-system contracts. The repair is not to give up host-native values. It is to require that members agree or refuse: keep Go's exactness, force the weaker host to fail loudly rather than round quietly, and turn the portable core into a normative profile with a stated numeric domain that every member computes identically. Rule 8 is already most of the way there.

Verdict: a sound way to *implement* an expression language, attached to an unsound account of what the language *means*, in a setting where meaning is the entire point. Adopt the four wording changes above and the concept is the best available answer for JSONata in OpenBindings. Ship it as written and the project will spend its first year explaining why the same transform returns different values from its own two SDKs and calling that correct.
