# Iteration-4 panel: programming-language and specification skeptic

Cold read of `e57816b`. Lens: attack the concept; then audit the semantic commitments in the API and the ledger.

## Grades

| Criterion | Grade | One-line justification |
| --- | --- | --- |
| Idiomatic fit for Go | B+ | `Compile`/`MustCompile`/`String` mirror `regexp`, `errors.As`/`Is` with sentinels is right, `iter.Seq` is current; the `(value, present, err)` triple is un-Go-like but honestly forced by undefined-versus-null. |

| Performance headroom the API permits | B+ | By-reference admission, lazy views, per-field selection, and budget-before-allocate are all right; `json.Number` re-parsed on every read is a stated cost with no cached alternative. |

| Overall | B- | A strong engineering design carrying a philosophy that does not survive its own ledger; fix the framing and this is an A- design. |

## Attacking the concept

**(1) Documentation as authority.** Steelman: the JSONata documentation is a tutorial with examples. It has no grammar with precedence tables beyond prose, no evaluation-order rules, no definition of "sequence" that survives edge cases, no numeric model, no string model, no regex dialect, no error catalogue. Its strongest normative statements are incorporations by reference: `$string` "using JSON.stringify", `$round` "round half to even", `$match` "regular expression". Each incorporation drags in ECMAScript: `JSON.stringify` is defined over ECMAScript Numbers (binary64), "regular expression" in that document means a JavaScript `RegExp`, and "characters" in a JavaScript document means UTF-16 code units unless it says otherwise. So the README's claim that "the documentation never says what a number is" is false by one hop: it says what `$string` of a number is by naming an algorithm whose input domain is binary64. The package then applies the algorithm's notation rules (thresholds at 1e-6 and 1e21, shortest round-trip) to a different value domain (exact integers, `*big.Int`) and labels the result "documentation, which specifies JSON.stringify". That is a reading of the documentation, and a defensible one, but it is not the documentation deciding. And the ledger already knows this: it has an **interpretation** column value and a **value model** column value that the README's two-way split ("documentation wins where it speaks, value model where it is silent") does not admit. There is also a fourth thing neither names: silence on a *language* matter (regex dialect, evaluation order of constructor fields, what `$` is inside a group). The README routes that silence to "the value model", which is a category error; a regex dialect is notation, not value.

Does it land? Yes, against the slogan; no, against the practice. The practice (read the documentation closely, choose readings, write them down) is exactly what a spec-less language needs. The slogan "documentation is the authority" should become "the documentation, read under a published authority ladder, is the authority".

**(2) Host-native value model.** Steelman: JSONata exists in OpenBindings to move values between systems, and a document author writing a transform has no idea which member will run it. "Two members differ where their models differ, and that is correct" is an abdication for that purpose; it means a transform's result is a function of the client's language. Worse, the API does not actually implement "the host's value model". Go has no rule that `float64(3)` is an integer, no promotion from `int64` to `*big.Int` on overflow, no refusal of `int64 + float64`. The package defines its own numeric tower and uses Go types as carriers. That tower is a *specification*, written in a doc comment, and it is a better one than binary64. So the honest statement is "this member defines a numeric model, here it is", not "the host defines what a number is".

Does it land? The abdication attack lands squarely and the README's own "portable core" paragraph is the confession: it is the profile authors must stay inside to get portability, and the README calls it "an observation, not a rule". The "host-native is decorative" attack lands too: the phrase is doing rhetorical work the design does not need.

**(3) The regex analogy.** Steelman: Go's `regexp` does not claim to implement PCRE per PCRE's manual with a ledger of divergences. It publishes its own syntax document (RE2 syntax), names its matching semantics (leftmost-first, with a documented `Longest` switch), and says what it does not support. Regular expressions also have a formal core (regular languages); the notation's meaning is mathematically defined and only the tie-breaking policy is engine-specific. JSONata has no such core. The analogy borrows credibility from a domain with a formal foundation. And where the analogy is faithful it argues against the README: regexes are famously *not* portable across engines, and everybody accepts that a regex "works in Go" or "works in JS". OpenBindings needs the opposite property for document-supplied transforms.

Does it land? As an argument for host-native strings and by-reference values, the analogy is fine and decorative. As an argument for the authority model it is load-bearing in the wrong direction: the `regexp` precedent says "write your own semantics document", which is what a PL person wants anyway (see below).

**(4) Declared divergence as sufficient discipline.** Steelman: divergence from *an implementation's observable behavior* (the wording in `jsonata.go`'s Conformance section) is not enumerable; there is no decision procedure for "have I declared every departure" without a specification. Divergence from *the reference suite* (the README's rule 6 wording) is enumerable but only covers what fixtures exercise. The two documents say different things. Then rule 6 says a departure "is permitted only where the value model cannot represent a reference value". Apply that to the ledger: `"0.3"` is representable; `2.68` is representable; `["2","10","b","a"]` is representable by `*Object`; UTF-16 sort order is representable; keeping the last duplicate key is representable; the D2014 range cap is representable; the reference's `$power(2,64)` result is a float64. Only the function-valued-result row and, arguably, the exact-integer rows satisfy rule 6. The ledger is mostly out of policy. Finally, two rows say "pending ruling"; a pending ruling is not a declaration, and the package doc has already ruled on both of them (`$round(2.675, 2)` is `2.67`; regex literals compile under Go's `regexp`, which is RE2).

Does it land? Yes. The discipline is right in spirit and undisciplined in letter: the ledger contradicts the rule that authorizes it, the two documents disagree on what is being declared against, and the ledger is declared in the wrong place for the person it affects (a document author reads the OpenBindings spec, which pins the documentation, and never sees a Go member's `DIVERGENCES.md`).

**(5) Choosing JSONata at all.** Steelman: CEL has a language definition, a conformance suite that every implementation must pass, a numeric model in which overflow is an error and int/double do not mix implicitly (almost exactly what this package wants), native Go and protobuf evaluation, non-Turing-completeness, and cost budgeting. JMESPath has a spec, a compliance suite, and a JEP process. jq has no spec either, but gojq is the direct precedent for this whole repository: a Go reimplementation with exact big integers, sorted object keys, and a "differences from jq" section, and it treats the reference *implementation* as the authority, which is the safer stance. JSONata brings lambdas, `$eval`, higher-order functions, and closures, all of which make static analysis (`Reads`, the selection planner) and budgeting hard, and its documentation was never written to be read as a specification.

Does it land? Partially. The choice is made upstream (Core pins JSONata 2.1) and JSONata's object constructors are genuinely the best authoring ergonomics for transforms. But the project should say out loud that it is paying a spec-less-language tax and that this evaluator class, plus the ledger, plus the portable core, *is* that tax. The class is not a philosophy; it is remediation.

## What a PL person would want instead

Ranked by value per effort:

1. **A normative semantics for the profile actually used** (the "portable core"), owned by this repository, with a fixture set. Value domain, sequence flattening and singleton rules, undefined propagation through each operator, object constructor and grouping, environment and shadowing, the standard-library functions in the profile. A few pages of operational rules. This is the single change that makes "conformance" mean something for OpenBindings authors, and it is cheap because the profile is small.

2. **A numeric model document**, separate from the doc comment, that a ledger row can cite. Representations admitted, the classification function, the integrality rule, the exact/inexact boundary, division and remainder, rendering. It should be written as a set of laws (substitutivity of equal values, exactness of carriage, closure of integer operations) and each law should have property tests. Two of those laws are currently violated (below).

3. **An authority ladder in the README**, replacing the two-way split: documentation text, then authority the documentation incorporates by reference, then a recorded interpretation where the text admits readings, then the value model where the documentation is silent on values, then an engine refusal. Every ledger row names its rung. This is a wording change and it fixes most of the internal inconsistency.

4. **A machine-checked ledger.** Each row is a fixture id, the reference's expected value, this member's expected value, the rung, and a reason. The suite runs the divergent fixtures and fails if the member does *not* diverge (a declared divergence that is not observed is a stale claim) and fails if the fixture's upstream content changed (the pin).

5. **Differential fuzzing** against the reference over generated expressions inside the profile, using a shared value corpus. Medium effort, high payoff, because it finds the silences nobody wrote down.

6. **A documentation audit table**: for every sentence of the pinned documentation that bears on behavior, a tag: defines / example only / incorporates / silent. This is the artifact that turns "documentation as authority" into a method. Larger effort; do it incrementally, function by function, as fixtures are pinned.

## Semantic commitments in the API and the ledger

**Absence versus null.** `(value, present, err)`, `NoInput` root-only, `ObjectView.Get` ok==false is absence. Sound and the single best decision in the file. Left undefined: whether a nil value in `Env.Bindings` is null (presumably) and that there is no way to bind absent; say so.

**Nil collections.** Nil `[]T` is the empty array, nil `map[string]T` the empty object, nil pointers null, nil `[]byte` empty bytes. A pragmatic choice, well argued in the comment (`$count(items) = 0`). Consistent with rule 4 only because carriage returns the nil slice itself. Note that a nil `*Object` is null while a zero `Object` is empty, so a caller who forgets `NewObject` gets a different JSON value; acceptable, but it is the one place a Go zero value is null rather than empty.

**Integrality and the 2^53 cap.** The comment commits to "every operation that observes a number is a function of that value, never of the representation", then commits that a float64 that is "integral beyond 2^53 is a decimal". Those conflict. `float64(9007199254740994)` and `int64(9007199254740994)` denote the same value and, by the equality rule, are equal. Add 1 to each: the int64 path yields the exact `9007199254740995`; the float64 path is decimal + integer, converts `1` exactly, and rounds the result to `9007199254740996`. Equal operands, unequal results: substitutivity fails. Every integral float64 is exactly some integer, so the cap is not needed for exactness; it exists to keep `1e300` from becoming a 301-digit integer. That is a representation judgment, which the comment says it never makes. Either drop the cap (an integral float64 is an integer of any magnitude, bounded by `MaxIntegerBits`, with the rendering consequence that `1e300 + 1` prints as digits) or keep it and rewrite the claim: "an integral float64 of magnitude at most 2^53 is an integer; beyond that it is a decimal, which is a representation the arithmetic observes".

**The exact/inexact boundary.** "An operand is never converted inexactly" is stated as the principle, and `CodeInexact` enforces it for integer-to-float conversion. But `Unmarshal` and `json.Number` classification decode the token `9007199254740993.0` to float64 `9007199254740992` and the comment pre-empts the objection by fiat ("that float64 is what a decimal is in this model, not a rounding of a result"). That is a definition, and it is inconsistent with rule 5 (comparison "by mathematical value"): the mathematical value of that token is odd, and `9007199254740993.0 = 9007199254740993` evaluates false here while it is true in mathematics and true in the reference. Transforms run over decoded payloads, so this is the boundary that matters. The principled alternatives are an exact decimal representation for fractional tokens, or honesty: retitle the principle to "an *integer* is never converted inexactly; a decimal token is its nearest float64 at decode, which is where a decimal's precision is fixed". Do the second now; note the first as the model a future member could adopt.

**Division.** "Rounded once to float64" is a clean rule, but the worked example is wrong. `1758000000000000123 / 1000000` is exactly `1758000000000.000123`; the float64 ulp at 1.758e12 is 2^-12 ≈ 0.000244, so the nearest float64 is `1758000000000.000244…`, whose shortest round-trip rendering is `1758000000000.0002`, not `.0001` (which is not the shortest rendering of any float64 in that neighborhood). The example is also the microsecond-timestamp case a user would care about, and it shows the model silently dropping two of the six sub-second digits under the banner of "never approximates". The principle is really "refuse where refusing is cheap, round once where refusing would make `/` unusable". Say that; it is defensible.

**`$string` and `JSON.stringify`.** Ledger row 1 cites "documentation, which specifies JSON.stringify", then applies that algorithm to values `JSON.stringify` cannot receive (`*big.Int`). The rendering thresholds are ECMAScript's; the value domain is this package's. The correct rung is "incorporated authority, applied over this member's value model". Also, this row contradicts the README's portable core, which lists `$string` among the functions where "the documentation and the reference agree without exception". A payload containing `0.30000000000000004` renders `"0.3"` in the reference and `"0.30000000000000004"` here with no arithmetic at all. Remove `$string` of numbers from the profile or qualify it.

**`$round` ties.** The ledger says "interpretation… pending a ruling"; the package doc says "2.67, a declared divergence". One of them is wrong about whether a decision has been made. Also, the ledger's own reasoning ("the float64 is identical on every host, so this is an algorithm choice") is a *good* argument that this is a language-level interpretation and should be uniform across members; it undercuts the README's "members may differ" stance for exactly the right reason.

**Regex dialect.** Ledger: "pending ruling, value model: the documentation is silent". The doc comment: regex literals compile in `Compile`, `${name}` is not recognized, `$replace` follows `$N` and `$$`. That is Go `regexp`, hence RE2, hence no lookaround and no backreferences, so `$match(s, /(?=x)/)` is a syntax error here and a working expression in the reference. This is the divergence with the largest practical blast radius in the whole ledger, it is not a value-model question, and it is undeclared. Declare it now as an interpretation of a silence, with an S code at `Compile`.

**Member order.** Maps observe sorted byte order, `*Object` insertion order, views their own order; equality ignores order; `$string`, `$keys`, `$each`, `$merge` observe it. Internally coherent, but it makes representation observable for objects in a way the package refuses for numbers: the same JSON text decoded by `encoding/json` versus `Unmarshal` yields different `$keys`. The package should state plainly that order is a representation property and that rule 5's "never by host type" applies to *values*, not to order. The ledger's reasoning for the reference's integer-key ordering ("ECMAScript's own-property order") is exactly right and is again an incorporated authority, not a value-model silence.

**Bytes.** `[]byte` is a string for every observing purpose, encoded lazily under `Env.BytesEncoding`, error without one. Coherent with the README's "binding chooses the encoding". Left undefined: whether `$type(b)` needs the encoding (the comment lists `$type` among content observations, but `"string"` is decidable without content), and `$boolean` of empty bytes. Ordering "by their encodings" means base64 order, not byte order; declared, fine.

**Closed environment versus `Resolver`.** README rule 7: "No expression can reach host state." The API: `ObjectView.Get(ctx, key)` is a host function the expression drives "with any key, in any order, as many times as the work bound allows". The doc comment is honest ("the boundary of the closed environment"); rule 7 is not. Restate rule 7 as "no host *functions* as language values; host *data* only through caller-supplied read-only views".

**Selection versus rule 9.** Rule 9: a selected field "is identical to the same field of a complete evaluation". The API: "When Complete would succeed, Select returns the same field", and "Select is not a guard". So when Complete would fail (a sibling field errors, or the whole evaluation exceeds a budget the partial one does not), Select returns a value and Complete returns an error. That is observable, and rule 9 should carry the qualification the API already has. Separately, `ReasonArrayInput`'s explanation ("each field's value is evaluated over the whole input") describes a case in which fields are still independent; the actual whole-input dependence for literal keys is emptiness (an empty array input yields `{}`). The reason is fine as conservatism; its stated justification does not justify it.

**`Reads`.** "A reference to a name that is not bound in the expression itself (an Env binding) makes known false." A binding read is not an input read; this looks like conservatism without a reason. Either explain it or drop it.

**Error codes.** `Code` doc: "the language's where the documentation or the reference implementation defines one". The documentation defines no codes; every S/T/D code is a reference-implementation artifact. So the reference *is* an authority for error identity, and the README's "the documentation defines the language" does not cover it. Declare that rung ("error codes are taken from the reference implementation as the only catalogue there is"). The claim "Class() == ClassEngine identifies behavior another member might not share" is an overclaim: `$power(10, 400)` is D3061 in the reference and a value here, so D-coded behavior differs across members too. `D1001` for a non-finite *input* extends a reference code to a situation the reference does not reach; minor, but "raised only in a situation the language defines for it" is then not literally true.

**Rule 3.** "Owes no more than its host offers and must not offer less" is vacuous as written: Go offers wraparound int64 addition and the package offers `*big.Int` promotion instead (more), and Go offers `complex128` which is not admitted (less). Replace it with the actual commitment: the member's value model is stated, and it is built from host types without an intermediate tree.

**Rule 1 versus the authority claim.** Membership requires passing the reference suite, which encodes reference behavior including departures from the documentation. The two are reconciled only through the ledger, so the ledger is load-bearing for membership, yet rule 6 restricts it to unrepresentable values. Circular as written.

**Duplicate keys at `Unmarshal`.** Fine as an engine refusal, but note the coupling it exposes: to receive the documented semantics (exact integers, ordered objects) a binding must decode with this package's `Unmarshal` or construct `*Object`/`*big.Int` itself. The README's "the binding has already decoded the wire" story hides that the value model reaches back into the decoder.

## What I would change

1. **Replace the README's two-way split with an authority ladder, and rewrite rule 6 to license it.** Under "The split": "Behavior is decided, in order, by: the documentation's text; an authority the documentation incorporates by reference (JSON.stringify, 'regular expression', 'characters'), applied over this member's value model; a recorded interpretation where the text admits more than one reading; the value model where the documentation is silent about values; an engine refusal. A member's ledger names the rung for every entry." Rule 6: "Divergences are declared, never silent. A departure from the reference suite is recorded with its rung, its reason, and the fixture it departs from, so a fixture change invalidates the declaration. An entry marked pending is not a declaration; the member's behavior is undefined there until it is ruled." Change `jsonata.go`'s Conformance paragraph from "the reference implementation's observable behavior" to "the reference suite", so the claim is finite and checkable.

2. **Publish the numeric model as a document and repair its two broken laws.** Either delete the 2^53 cap ("a float64 whose value is integral takes part in arithmetic and comparison as that integer, whatever its magnitude, bounded by Limits.MaxIntegerBits") or keep it and strike "never of the representation". Rewrite the principle as "an integer operand is never converted inexactly; a decimal token becomes its nearest float64 when it is decoded or first read, and that is where a decimal's precision is fixed; a non-integral result of exact operands is rounded once". Fix the example to `1758000000000.0002` or choose one that does not lose digits.

3. **Make the portable core a named, tested profile.** "The OpenBindings transform profile" with a fixture set every member must pass identically, and remove `$string` of numbers (and `$type`/comparison on integers beyond 2^53) from it, or qualify them. Change "An observation, not a rule" to "A rule of the project, not of the class".

4. **Rule on the regex dialect now, in the ledger and the doc comment.** "Regular-expression dialect: RE2 as implemented by Go's regexp. Lookahead, lookbehind, and backreferences are not supported and fail at Compile with an S code. Authority: interpretation of a silence; the documentation says 'regular expression' in a JavaScript document, and this member reads it as the host's engine." Add the same ruling to the `$round` row, dropping "pending".

5. **Restate rules 7 and 9 to match the API.** Rule 7: "The language has no host functions. Host data enters only through caller-supplied read-only views, and the member documents that a view is a door." Rule 9: "A field obtained by selective evaluation is identical to the same field of a complete evaluation that succeeds; a complete evaluation may fail where a selection does not, and selection is therefore not a guard."

## On the concept

The good idea underneath this repository is real and worth defending: the JavaScript reference implementation is not sacred, its binary64 numbers and UTF-16 strings are accidents of its host, and a Go evaluator that carries integers exactly, refuses to approximate, budgets everything, and reads host values by reference is a better tool for the OpenBindings job than a faithful port would be. The API expresses that idea with unusual care. The absence triple, the lazy byte encoding, the `Resolver` as an explicitly named door, the budgets, and the selection contract are the work of people who have thought hard about where semantics hide.

The philosophy wrapped around it does not hold. "The documentation is the authority" fails on contact with the documentation, which is a tutorial that incorporates ECMAScript by reference in exactly the places where the package departs from ECMAScript, and the ledger already proves the point by needing four kinds of authority where the README grants two. "The host defines the values" is decorative: the package defines its own numeric tower and uses Go types to carry it, which is the better design and should be claimed as such. The regex analogy, followed faithfully, tells you to write your own semantics document the way `regexp` did, and it tells you that host-native notations are not portable, which is the property OpenBindings most needs and the property the README waves away with "that is correct". And rule 6 as written forbids most of the ledger.

None of that requires changing the code. It requires the README to say what the ledger already knows (a ladder of authorities, each divergence naming its rung), the numeric model to be a document with laws and property tests rather than a doc comment with one wrong example, the "portable core" to become a tested profile rather than an observation, and two pending rows to be ruled on since the API has already ruled on them. Do that and the concept becomes what it should have been from the start: not "the documentation is the authority" but "here is a specification of what we read the documentation to mean, here is the small profile where every member agrees, and here is the exact list of places we knowingly differ from the program everyone else copies". That is a claim a PL person can check.
