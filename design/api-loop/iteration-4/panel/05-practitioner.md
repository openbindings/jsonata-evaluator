# Iteration-4 panel: JSONata practitioner

Cold read of `e57816b`. Lens: a JSONata practitioner (Node-RED, Step Functions, jsonata-js).

## Grades

| Criterion | Grade | One-line justification |
| --- | --- | --- |
| Idiomatic fit for Go | B+ | Reads like `regexp` plus `encoding/json` (Compile/MustCompile, Unmarshal/Marshal, ctx, `errors.Is`); the `(value, present, err)` triple is unusual but it is the only honest way to carry JSONata's undefined into Go. |
| Ergonomics of the common path | B | `Compile`, `Unmarshal`, `Eval`, `Marshal` is four lines and `EvalJSON` is one; the tax is that "an object" comes back as either `map[string]any` or `*Object` depending on whether it was carried or constructed, so every consumer of a result writes the two-arm switch or reaches for `Member`. |
| Correctness and footgun risk | B- | The number model is more careful than jsonata-js and the traps are declared, but two of them bite ordinary expressions: `&` renders floats differently from every Node-RED flow ever written, and `x * 1e-9` fails where `x / 1e9` succeeds on the same input. |
| Performance headroom the API permits | A- | Carriage by identity, views over foreign values, `Reads()` for partial fetch, selective evaluation with shared budgets, budgets as work not time; nothing in the surface forces a copy or a serialization. |
| Concept soundness (JSONata-as-regex, documentation-as-authority, host-native values) | B- | Host-native values is right and the results prove it; documentation-as-authority is only half a spec because the JSONata docs are prose with examples, and the ledger's own "pending ruling" rows show the docs run out exactly where users have questions. |
| Overall | B | I would choose this over a faithful port for the stated job (large IDs, protobuf, exact carriage), and I would not hand it to a Node-RED user without the ledger stapled to the front. |

## Would my expressions mean the same thing?

1. `{ "id": user_id, "name": display_name }` over a decoded JSON object. Same. This is the portable core and it is identical; absent `display_name` omits the key in both.

2. `items[price > 10 and $exists(sku)].name` and `items[-1]`. Same. Predicates, negative index, singleton unwrapping and sequence flattening are owed in full and the doc comments give me no reason to expect otherwise. One question below about `items[1.5]`.

3. `$sum(items.(price * qty))` where `price` is `19.99` and `qty` is `3` in the JSON. Same. `qty` is an int64 here, converts exactly to float64, and the float64 multiply and left-to-right `$sum` are the same IEEE operations V8 performs. The common arithmetic path is bit-identical; that matters and the doc comment earns it.

4. `"Total: " & $sum(items.(price * qty))` with `1.1` and `3`. Different. jsonata-js: `"Total: 3.3"`. This library: `"Total: 3.3000000000000003"`. Declared (ledger row 1). This is the divergence a working JSONata user will hit first and most often, because `&` on a computed float is how everyone builds a message. The ledger is right that the docs say `JSON.stringify`, and the reference really does run `toPrecision(15)` in a replacer, so the entry is correctly grounded. But note the ledger's own example is wrong: with a 15-significant-digit replacer the reference renders `$string(1234567890123456789)` as `"1234567890123460000"`, not `"1234567890123456800"` (17 digits cannot come out of `toPrecision(15)`; that string is what `String()` gives without the replacer). Fix the example.

5. `$round(price, 2)` with `price` = `1.015` (or `2.675`, or any price whose third decimal is 5). Different. jsonata-js shifts the decimal spelling (`"1.015e2"` = `101.5`, half-to-even, `1.02`); this library rounds the binary value (`1.01499999…`, `1.01`). Declared (row 2), but marked "pending a ruling". Prices with a trailing 5 are not rare and invoice transforms do exactly this. I argue below that the ledger's reading is the weaker one.

6. `id = 1758000000000000123` and `$string(id)` on a snowflake ID. Different, and the library is right. jsonata-js: `1758000000000000123 = 1758000000000000000` is `true` (both collapse to the same float64), and `$string(id)` is `"1758000000000000000"`. Here the comparison is `false` and the string is the digits. Declared (row 3). This is the reason the library exists and it delivers.

7. `ts_ns / 1e9` versus `ts_ns * 1e-9` with a nanosecond timestamp (`1758000000000000123`, above 2^53). jsonata-js: both yield a rounded float. Here: the division succeeds (integer over integral-float `1e9`, exact quotient rounded once, `1758000000.0000002`), the multiplication fails with E1008 because the integer operand cannot convert exactly to float64 to meet the decimal `1e-9`. Declared only as "mixed integer and decimal arithmetic beyond 2^53 rounds silently / error E1008" (row 5); the asymmetry between the two spellings of the same computation is not declared and is the kind of thing that will look like a bug in production, since it depends on the data crossing 2^53.

8. `$keys({"b": 1, "10": 2, "2": 3})` and `$string($)` over a `map[string]any` input. Different. jsonata-js: `["2", "10", "b"]` (integer-like keys hoisted numerically). Here: `["b", "10", "2"]` for an `*Object`, `["10", "2", "b"]` for a map. Declared (row 6), but the row's headline is "integer-like keys" while the map case reorders every key, which is a larger delta than the row advertises and affects `$string`, `$each`, `$spread` and grouping order for anyone passing `map[string]any`. Users of `Unmarshal` get document order and are closer to the reference than the reference is to its own docs.

9. `$match(text, /(?<=\$)\d+/)` and `$split("😀👍", "")`. The first is undefined: the regex dialect is "pending ruling" (row 11), and if the answer is RE2 this fails at `Compile`, as do backreferences and negative lookahead, which are common in scraped-text cleanups. The second is different and declared (row 7): two code points here, four UTF-16 units in the reference. The ledger correctly scopes this to `$split("")` and `$match.index`; `$length` and `$substring` are already code-point aware in jsonata-js, so the doc comment's `$length("😀")` is 1` is agreement, not a divergence, and the ledger is honest about that.

10. `$replace(s, /(\w+)@(\w+)/, "$2 at $1")` and `$replace(s, /x/, "$$")`. Same for these. Undefined for `$0` (the docs say N = 0 is the whole match; the doc comment says only "the Nth captured group") and for `"$12"` with one group (the reference takes the longest prefix that names a real group and emits the rest literally, so `$12` is group 1 followed by `2`; the docs are silent).

11. `missing ?? "default"`, `count ?: 0`, `$x ?? "d"` where `$x` is bound to Go `nil`. Undefined by the doc comments. Nothing in the text says whether `??` treats null like undefined, and since a Go `nil` binding is null and there is no way to bind absent, a caller's "unset" variable lands on exactly the branch the docs are least explicit about.

12. `$ ~> |items|{"checked": true}|`. Same value. Undefined Go type: the transform operator deep-copies; the doc comments never say whether the cloned root comes back as `*Object` (constructed) or the input's map type, or whether untouched subtrees are carried or cloned.

## What a JSONata user gains and loses

Versus jsonata-js:

Gains. Integers are integers: IDs, counters, and protobuf int64 survive `=`, `$string`, `+ 1`, `$sort`, and carriage with no 2^53 cliff, which no JavaScript engine can offer. `Unmarshal` decodes without losing digits and `Marshal` writes a carried `json.Number` token back verbatim, so `1.50` stays `1.50` unless an expression touches it. Errors carry a code, a class, an offset, and a `Value` that is charged to a budget, so a `$error("…")` cannot blow up a log. Budgets are on work and bytes and cancellation is a ctx, where jsonata-js gives you a range cap at 1e6 and a stack. `Env.Now` makes `$now()` testable without shadowing it with a binding. `Reads()` tells a caller which input members an expression will touch, which jsonata-js users reconstruct by walking `ast()`. Selective evaluation is new. Strings are code points everywhere, not code points in `$length` and UTF-16 in `$split`, which is one fewer surprise than the reference.

Losses. No `registerFunction`, full stop, and `Env.Bindings` holds values only. Every Node-RED `$env`, `$flow`, `$global`, every Step Functions `$states`-style intrinsic, every "just register a `$lookupCustomer`" pattern is gone. For OpenBindings that is the design; for a general JSONata user it is the single biggest reason to keep jsonata-js. The regex dialect is undecided, and if it lands on RE2 then lookaround and backreferences, which jsonata-js users use freely, fail to compile. `&` on floats prints the honest float, which is more correct and less friendly than the 15-digit rendering everyone's flows were written against. `$round` on decimal ties differs. Objects with integer-like keys change order. No AST access. No async or callback functions. `$error` messages are not in `Error()`.

Versus a faithful port:

A faithful port gives me byte-for-byte parity with my Node-RED flows: 15-digit strings, decimal-spelling `$round`, hoisted integer keys, UTF-16 splits, JavaScript regexes, and every value a float64. Its cost is precisely the thing this class fixes: every integer above 2^53 is silently wrong, and no port can fix that without diverging from the reference. This library makes the opposite trade: fewer parity guarantees, more correct values. For a corpus of existing expressions the port wins on day one; for an API-payload transformer that must never corrupt an ID, this design is the only one that can be right, and its ledger is short enough to read in a minute.

## What I would change

1. Fix the README's "portable core" claim, which is false on the project's own first member. `$string`, `$keys`, `$merge`, and `$sift` are all in the ledger (`$string` of any non-integral float; the other three on integer-like keys). Replace "That subset is exactly the part of the language where the documentation and the reference agree without exception" with: "Within that subset the documentation and the reference agree, with three exceptions every member declares: `$string` of a non-integral number, `$string` of an integer beyond fifteen digits, and the member order of objects with integer-like keys as observed by `$keys`, `$merge`, and `$sift`. Authors who avoid those get identical results from every member."

2. Rule `$round` the reference's way, and ground it in the package's own `$string` rule so it stays "by value". Proposed doc-comment wording: "`$round(x, p)` rounds the decimal digits that `$string(x)` renders, half to even, and yields the float64 nearest the rounded decimal, so `$round(2.675, 2)` is `2.68` and `$round(1.015, 2)` is `1.02`. The shortest round-trip spelling is a function of the value, so this is still rounding by value and identical on every host." The ledger's "algorithm choice" argument cuts the other way: the docs say "decimal places", motivate half-to-even with financial rounding, and never mention binary ties; the shortest-decimal reading is the one a person who wrote `2.675` in their data expects, and it removes a ledger row rather than parking one as "pending". Also correct the row's "only non-tie decimal examples": `$round(11.5)` and `$round(12.5)` in the docs are ties, just exactly representable ones.

3. Remove E1008 by applying the division rule to every mixed operation. The package already states the principle, "an operand is never converted inexactly, while a non-integral result of exact operands is rounded once," and applies it to `/`. An exact integer times, plus, or minus a float64 (a dyadic rational) is exactly computable and can be rounded once. Proposed wording, replacing the `CodeInexact` sentence: "An integer operand combined with a decimal operand is computed exactly and the result rounded once to float64, so `9007199254740993 + 0.5` is `9007199254740993.5` rounded to float64 and `1758000000000000123 * 1e-9` agrees with `1758000000000000123 / 1e9`." Then delete `CodeInexact`, `ErrInexact`, and ledger row 5. If the refusal stays, at minimum the doc comment must state the asymmetry in one line: "`x / 1e9` succeeds where `x * 1e-9` fails for the same `x` beyond 2^53."

4. Rule the regex dialect now and finish `$replace`. Proposed wording: "Regex literals are Go `regexp` syntax (RE2). Lookahead, lookbehind, and backreferences are not supported and fail at `Compile` as a syntax error (S code) naming the construct. `\b` is an ASCII word boundary as in JavaScript without the `u` flag. Matching is over code points, so `.` never matches half a character." And for `$replace`: "`$0` is the whole match; `$N` is the Nth group; a `$` followed by digits naming more groups than exist takes the longest prefix that names a group, as the reference does, and a group number with no such prefix is the empty string." Add an "RE2 dialect" row to the ledger with the unsupported constructs listed.

5. Let `$error` speak. The expression author wrote the message to be read. Proposed wording for `Error`: "`Error()` renders Code, Message, and Offset, and for ClassRaised also Value when it is a string, because the expression supplied it as the message; Message never includes content derived from the input except through Value on a raised error." If the privacy rule must stay absolute, then say plainly in the `$error` sentence: "the message you passed to `$error` is in `Value` and not in `Error()`; log it yourself." Today a Node-RED user who does `$error("no such order: " & id)` will see a log line reading `D3137` and nothing else.

## Things the doc comments leave unclear to a JSONata user

- `??` and `?:`: does `??` fall through on null as well as undefined? With Go `nil` meaning null and no way to bind absent, this decides what an "unset" binding does.
- `=` and `!=` with an undefined operand: the reference returns `false` for both `missing = 1` and `missing != 1`, and absent for `missing < 1`; the docs do not say; which does this package do?
- `$number` on a string: `$number("9007199254740993")` returns int64 or float64? `$number("12345678901234567890")` returns `*big.Int`? `$number("1e3")` is an integer by value? Hex/octal/binary prefixes beyond int64?
- `$formatNumber`, `$formatBase`, `$formatInteger`, `$parseInteger`, `$fromMillis` with a `*big.Int` argument: exact, error, or E1008?
- `$now()` output precision and format (the reference renders milliseconds and `Z`); what happens when `Env.Now` returns nanoseconds.
- `$type` of a `[]byte` with no `BytesEncoding`: the sentence lists `$type` among purposes that "observe content", so is `$type(bytes)` an error rather than `"string"`?
- The Go type of a sequence result: is `items.name` a `[]any`, and does the sequence-versus-array distinction (`[items.name]`, `items.name[]`) survive into the returned value?
- The transform operator: type of the cloned root, and whether unchanged subtrees are carried or copied.
- A function value nested inside a result (`{ "f": function(){1} }`): E1001 for the whole result, or the field omitted, or rendered as `""` the way `$string` does?
- "object keys" in the sentence "every operation that observes a number (… object keys) is a function of that value": which operation is meant, given a numeric key in a constructor is T1003?
- `items[1.5]` and `items[$bigint]`: floored as the reference does, error, or absent?
- `$split` and `$match` with a pattern that matches the empty string (the reference raises D1004 to avoid an infinite loop); is that a language code here or a budget?
- `$sum([])` returns int64 `0`? `$max([])` absent? `$average([])` absent or D1001?
- Unmarshal refuses an unpaired surrogate escape and the engine refuses invalid UTF-8 strings; `JSON.parse` accepts the former and JavaScript strings hold the latter. Neither is in the ledger.
- Can `$random` be seeded for tests the way `$now` can via `Env.Now`?
- `Plan.Reason` says "a function the planner has not qualified", but not which function or which field; a user tuning an expression for selection has no way to find out short of bisecting.
- `Reads()`: does a predicate's path count (`items[price > 10].name` reads `items.price`)? Does `$$` at top level, outside a function, keep `known` true?
- `$string` of a `*big.Int` nested in an object, and `$string` of a `float32` input (widened, so `$string(float32(0.1))` is `"0.10000000149011612"`?): stated for `Marshal`, not for `$string`.
- `$now`, `$fromMillis` picture strings: is the full XPath F&O date picture implemented, including `[F]`, `[W]`, ordinals, and widths? "Every standard-library function in full" is the README's promise; the package doc never says it.

## On the concept

Host-native values I trust without reservation, because I have been burned by the alternative: every JSONata engine I have used turns `1758000000000000123` into something else, and no amount of fidelity to the reference can fix that, since the reference is the source of the defect. The regex analogy holds here. Nobody wants PCRE's string model in Go; nobody should want V8's number model in Go either. Carriage by identity and comparison by value are the two rules that make it work, and the doc comment states both crisply.

Documentation as authority I trust about half as far. The JSONata documentation is prose with examples, written after the implementation, and it is silent or ambiguous on exactly the things this review had to ask about: the regex dialect, undefined in equality, `??` on null, `$replace` group numbering, `$round` on ties. The README's own rule, "the value model wins where the documentation is silent," means that in each of those places the host decides, and hosts decide differently. That is honest, and the regex world lives with it, but a JSONata user's expressions are not written against the documentation; they are written against jsonata-js, and the class quietly admits this in membership rule 1, which verifies against the reference test suite. So the authority in practice is "the reference suite minus a pinned ledger," and that is the thing I would actually trust, provided the ledger stays short, its examples are right (row 1's is not), and nothing sits in it marked "pending". The `$round` row is the tell: "documentation wins" invites relitigating every fixture where the docs are vague, and a user who needs an answer today gets "pending a ruling on the numeric model."

Would I rather have a faithful port? For a Node-RED flow library, yes, and I would not use this for that. For what OpenBindings is doing, running author-supplied transforms over API payloads where an ID must survive intact and a bad expression must not take down the process, no: a faithful port cannot be correct there, and this design can, with a ledger I can read in a minute. The gap between the two is not the concept, which is sound; it is the five things above, three of which are wording and two of which are rulings that should be made before anyone writes `$round(price, 2)` against it.
