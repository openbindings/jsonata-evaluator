# Iteration-3 panel: programming-language and specification skeptic

Cold read of `b501e30`. Lens: attack the concept; then audit the semantic commitments in the API and the ledger.

## Grades

## Attacking the concept

### 1. Documentation as authority

Steelman: the JSONata documentation is a tutorial with a function-by-function reference. It has no grammar, no evaluation rules, no type system, no definition of "number", and it incorporates other authorities by reference: `JSON.stringify` (ECMAScript) for `$string`, XPath F&O 3.1 picture strings for `$formatNumber`, `$formatInteger`, `$fromMillis`, `$toMillis`, and, I believe, JavaScript's regex syntax for regex literals (the ledger claims silence here; verify against the pinned page before relying on that). Each incorporated authority brings its own value model. ECMAScript's `JSON.stringify(9007199254740993)` is `"9007199254740992"`: the incorporated authority *does* say what a number is, and it says the opposite of what this package does. The README then treats the same incorporation as decisive for the digit algorithm (shortest round-trip) and as void for the number model. That is not "documentation as authority"; it is selective incorporation without a stated substitution rule. Same for member order: if `$string` is `JSON.stringify`, then `$string`'s member order in the reference is *specified* by the incorporated authority (ECMAScript's integer-key-first ordering), and the ledger's "documentation is silent" claim for that row is wrong at one remove.

Then the silence cases. The README says the value model wins where the documentation is silent. But rule 1 verifies against the reference *suite*, and the suite encodes reference behavior on hundreds of things that are neither documented nor value-model matters: error codes, `$split(s, "")` on astrals, `$number` parsing edge cases, sort stability, `$lookup` on arrays. On those, the operational authority is the reference. So the actual precedence has three tiers (documentation, value model, reference) and the README admits only two. Worse, when the documentation and reference agree, nobody consults the documentation; the suite is the only executable oracle. Operationally this class is "reference suite minus a ledger, plus documentation citations backing the ledger". That is a legitimate discipline, but the README's rhetoric ("every existing port takes the reference as authority... this class takes the documentation") overstates the difference: the difference is the *sign convention* on the delta and the willingness to write it down.

Does it land? Partially. "Documentation as authority" is coherent only with (a) an explicit precedence order, (b) a stated rule for incorporated authorities, and (c) an honest statement that the reference suite is the detection floor, not the authority. None of the three is written. With them, the position is defensible and better than what other ports do.

### 2. Host-native value model

Steelman: the README says "the host defines what a number is" and "no parity between members". But transforms are document-supplied contract text: an interface author writes `9007199254740993 = $.id` once and every consumer runs it. A JavaScript member that is honestly host-native (float64 only) answers `true`; this member answers `false`. The README calls that "correct". For a language used to move values between systems, that is the failure mode, not a feature. And the escape hatch, the "portable core", is an observation the README explicitly refuses to make a rule.

Also, the value model here is *not* the host's. Go's `/` on integers truncates; the package's `/` is exact-or-rounded-once. Go has no exact/inexact tower spanning `int64`, `*big.Int`, and `float64` with a `MaxIntegerBits` bound. Go's stdlib `strings.ToUpper("ß")` is `"ß"`; full case mapping needs `x/text`. The doc comment describes a designed numeric algebra, built from Go primitives, tailored for exact carriage of API payloads. That is good design. It is not "the host's". The README's framing ("what a number is... those are the host's") is rhetorical cover for a decision the member made.

Does it land? Yes, against the README; no, against the package. The fix is to lift the package's numeric model (exact integers to a bound, binary64 for everything else, spelling decides exactness, comparison always by mathematical value) to the *class* as a floor. Every host in scope has IEEE 754 binary64 and can do exact integers; "host-native" should mean "the host's *representation* of that model", not "whatever the host happens to have".

### 3. The regex analogy

Steelman: regex engines are the paradigm case of a notation with no specification whose per-host engines diverge observably: `.` and newline, `\d` and Unicode, `$` at line ends, backreferences, lookaround, possessive quantifiers. There is no "the regex notation"; there is POSIX ERE, PCRE, ECMAScript, RE2, each declaring incompatibilities, and users burned by all of them. Portability is achieved by testing against the target engine, which is exactly the thing an interface document cannot do. Regex engines also return positions and booleans; their results do not travel. JSONata results do. And the irony: the one unresolved ledger row is the regex dialect, where "host-native" (RE2) and "documentation" (if it names JavaScript syntax) collide head-on.

Does it land? Yes. The analogy is decorative for the argument it is meant to make and load-bearing for the opposite one. The strongest *correct* form of the argument is narrower: "implement natively, the way `regexp` does, because ports inherit bugs and foreign value models"; do not extend it to "notations are portable across native engines", because regex proves they are not without a shared spec. One place the analogy pays for itself and the README does not cash it: RE2's linear-time guarantee is a real security property that a JS-dialect backtracking port cannot give. Name it in the regex ruling.

### 4. Declared divergence as sufficient discipline

Steelman: rule 6 defines a divergence as "a departure from the reference suite". Anything the suite does not exercise is, by definition, not a divergence, so "never silent" is vacuous outside the suite. The suite is finite; the language is not. The declaration mechanism detects only what the suite detects and what an engineer happens to notice. Two concrete undeclared candidates from the doc comment alone: string ordering by code point diverges from the reference's UTF-16 code-unit ordering for astral characters versus U+E000–U+FFFF; `Unmarshal` rejecting duplicate member names diverges from the reference's last-wins parse. Neither is in the ledger.

Rule 6 also says a departure is permitted "only where the value model cannot represent a reference value". Four of the seven substantive ledger rows violate that: Go can trivially render 15 significant digits, round the decimal spelling, order integer-like keys first, and index UTF-16 code units. Those rows are justified by documentation-over-reference, which rule 6 does not admit and the README's earlier prose does. The ledger is consistent with the README's *spirit* and inconsistent with its *letter*.

Does it land? Yes, hard, but the remedy is cheap: redefine "divergence" as a departure from the reference's observable behavior, classify each entry (documentation says otherwise / documentation silent, value model decides / not in the documented language), make the suite the floor not the definition, and add a differential-fuzzing obligation against the reference so "never silent" is enforced rather than hoped.

### 5. Choosing JSONata at all

Steelman: JMESPath already *is* what this README wants: a written specification, a compliance suite, a JEP process, native engines in Go, Python, JS, Rust. RFC 9535 JSONPath has a formal grammar and a compliance suite. CEL has a spec and is Go-native. JSONata has one implementation, a tutorial, JavaScript's value model baked into its semantics (undefined versus null, sequence flattening, singleton unwrapping), JavaScript regex, JavaScript number rendering, and enough power ($eval, recursion) to need budgets. And the "portable core" is tiny: literals, conditionals, comparisons, and ten functions. That subset is a different language that JSONata syntax happens to express.

Does it land? Not against the decision, which the OpenBindings spec has already made and which buys real expressiveness (`$sift`, `$merge`, `$each`, lambdas) that JMESPath lacks. It lands against leaving the core as "an observation". The right response is to specify the portable core normatively, with a grammar and semantics small enough to be exhaustively tested, and say "beyond the core, JSONata per the pinned documentation". That gives OpenBindings a contract language that means one thing everywhere and a rich language around it that means "documented behavior".

## What a PL person would want instead

Ranked by value per effort:

1. **A precedence policy and a corrected rule 6** (hours). Normative prose > examples > incorporated authority read with the value model substituted > value model > reference behavior. Three divergence classes. Suite is the floor. This resolves most of the README's self-contradictions with wording alone.
2. **A class-level value-model floor** (a day). Extract the package's `# Numbers`, `# Strings`, and `# Objects` sections into a class document: exact integers to at least 64 bits, binary64 otherwise, spelling decides exactness, comparison by mathematical value, strings as scalar-value sequences, bytes as a distinct carrier. Members implement at least this; parity on the floor becomes a class property.
3. **A documentation-derived fixture set** (days). Every example in the pinned docs becomes a fixture with a citation. Then "verified against the documentation" is executable rather than aspirational, and doc/reference disagreements surface automatically as the ledger's inputs.
4. **Differential fuzzing against the reference** (days, ongoing). Generated expressions over generated values, reference versus member, with the ledger as the allowlist of expected differences. This is the only mechanism that makes "never silent" true.
5. **A normative specification of the portable core** (a week or two). Grammar, typing, evaluation rules, error conditions, for the subset OpenBindings actually needs. Highest long-term value; belongs in the OpenBindings spec rather than here.
6. **A full formal semantics of JSONata** (months). Not worth it; the language's own authors have not done it, and it would freeze interpretations the pinned documentation leaves open.

## Semantic commitments in the API and the ledger

**Absence.** `(value, present, err)` with absent only at the top level, containers dropping undefined members, `ObjectView.Get` `ok == false` as absence: sound and complete. Unrepresentable: an absent *binding*. `Env.Bindings` cannot bind a variable to undefined; an unbound name reads as undefined, so this is fine, but say so.

**Nil collections as empty, nil pointers as null.** Sound, well argued (`$count` of an unset slice). Note it silently makes `[]T(nil)` and `[]T{}` indistinguishable, which is correct for the value model.

**The admitted set.** `[]byte` is `[]uint8`, and `[]T` with `T = uint8` is also admitted, so `[]uint8` is both a byte string and a number array. `json.RawMessage`'s underlying type is `[]byte`, so the "named type whose underlying type is admitted" rule classifies it as bytes while the doc says it decodes as JSON. Both need a stated tiebreak: `[]byte` and `json.RawMessage` win by exact type, then named types with underlying `[]byte` are bytes, and a caller wanting a number array of small integers must use another width.

**Resolver as the boundary.** The doc comment is honest that this is a door. README rule 7 ("no expression can reach host state") is absolute and the API contradicts it: an expression drives caller code with expression-chosen keys, plus the clock and an RNG. Rule 7 should read "closed except for the clock, entropy, and a caller-supplied resolver that presents values, never functions".

**Prepare and Plan without ctx.** `ReasonArrayInput` requires classifying the root. If the root is foreign, that requires `Resolver.Resolve(ctx, ...)`; if it is a `json.RawMessage`, decoding charged to a budget. `Prepare(input, env)` and `Plan()` have no ctx and "check nothing". Either the plan is computed lazily on first `Select` (then `Plan()` before any `Select` is undefined for foreign roots) or `Prepare` takes ctx. Inconsistent as written.

**Number classification by spelling.** "Every admitted numeric representation denotes one numeric value" is contradicted by the classification rule: `json.Number("9007199254740993")` denotes 9007199254740993 and `json.Number("9007199254740993.0")` denotes 9007199254740992, so two spellings of one mathematical number denote different values, and `9007199254740993 = 9007199254740993.0` is `false`. This is Scheme's exact/inexact distinction with spelling as the exactness marker. It is a defensible model. It is not the model the doc claims ("a function of that value, never of the representation"). Name it as what it is. Also unstated: a token whose nearest float64 is infinite (`1e400`), at `Unmarshal` and at `Compile`.

**Entering the float domain.** `9007199254740993 + 0.5` is an error; `9007199254740993 / 2` is the exact quotient rounded once to float64, which silently yields 4503599627370496 (the `.5` is lost at that magnitude); `1758000000000000123 / 1000000` is documented as rounding "rather than failing". Rule 8 ("refuses rather than approximates... unrepresentable values are failures") is applied to `+` and waived for `/`, with no principle distinguishing them. Both lose the same information for the same reason. Either round once everywhere (compute the exact rational, round to nearest float64; the doc's own `/` rule already concedes that entering binary64 is definitional, not approximation) or refuse everywhere (which kills `1/3`). I would round once everywhere and reserve refusal for non-finite, division by zero, and `MaxIntegerBits`. Also undefined: `$average` "yields float64" but whether it divides the exact sum with round-once or converts the sum first; `$number` of a string beyond 2^53; `$formatNumber`/`$formatBase`/`$formatInteger` on `*big.Int`, which incorporate XPath's decimal model.

**Comparison across domains.** "Comparison never rounds through float64 when both operands are exact" leaves exact-versus-float64 comparison unstated. The "function of that value" rule implies exact mathematical comparison (so `9007199254740993 > 9007199254740992.0`); say it. If so, comparison is total across the domains where arithmetic refuses, which is fine and worth stating as a deliberate asymmetry.

**`$round`.** The ledger says the documentation is silent on the basis. It is not silent on the rule (half to even) and all its examples are decimal; the reference rounds the decimal spelling. Whether "half" is decided on the decimal or the binary value is an *interpretation* of documentation that speaks, not a silence. The entry's justification column should say that.

**`$string` of a float.** "Shortest decimal that round-trips" fixes the digits, not the notation. Go's `FormatFloat(f, 'g', -1, 64)` renders `1000000.0` as `"1e+06"` and `1e20` as `"1e+20"`; ECMAScript `Number::toString` renders `"1000000"` and `"100000000000000000000"`, switching to exponent form only outside `1e-7 < |x| < 1e21` and without zero-padded exponents. Since `1e6` and `1000000.0` are float64 in this model, `$string(1e6)` is at risk of `"1e+06"`. The commitment "as the documentation specifies by reference to JSON.stringify" requires ECMAScript's notation rules; state them.

**Strings.** Code points, full case mapping, code-point ordering: sound. Undeclared: code-point ordering differs from the reference's UTF-16 ordering for astral versus U+E000–U+FFFF strings in `<`, `$sort`, `$min`/`$max`. Unstated: `Unmarshal` on lone surrogate escapes (`"\uD800"`), which the reference preserves and `encoding/json` replaces with U+FFFD; under "invalid UTF-8 is an error" the answer is presumably rejection, and that is another wire-decoding policy (see Unmarshal below).

**Bytes.** Rule 5 says comparison is "never by host type". The API orders `[]byte` against `[]byte` by raw bytes, `[]byte` against `string` as a T2010 error, and equates `[]byte` with `string` by encoded content. Raw-byte order is not the order of the base64 presentations (the base64 alphabet is not byte-order preserving), so two `[]byte` values that "are strings" for `$type`, `$length`, and equality sort differently from their string selves, and a mixed sort is refused by host type. Pick one: bytes are strings and compare as their presentation, or bytes are a fourth primitive with `$type` reporting `"string"` as a documented lie and cross-type ordering refused with an *engine* code. The current mix violates rule 5.

**Objects and order.** `*Object` insertion order, maps sorted, equality order-insensitive and representation-insensitive: sound and complete. The `*Object`/`map` union in results is a real cost but consistent with "only carriage preserves representation". `ObjectView` order is stated for `$keys` only; say it governs every order-observing operation.

**Carriage.** "Same Go value, same type, same identity" including foreign values: sound, and correctly implies the result space is admitted ∪ foreign ∪ `*Object`. Aliasing rules are stated. A function value cannot leave: fine, but the reference returns function objects, so the suite may contain a fixture this refuses; check and declare if so.

**Errors.** Engine refusals wearing language codes is the systemic defect. D1001 (the language's "number out of range", raised by the reference for infinities) is reused for `MaxIntegerBits` overflow and for inexact mixed conversion, neither of which the language defines; a caller cannot distinguish "your data produced infinity per the language" from "this engine's stricter model refused", and the whole point of `Class` is that distinction. Every other `Limits` field yields `CodeBudget`; `MaxIntegerBits` yields D1001. T2010 for bytes-versus-string ordering is the same mistake. `CodeUnsupportedValue` also absorbs `Unmarshal` syntax errors, which are not unsupported values. The `Is`-by-code design and the recovered-panic policy are sound.

**Limits.** Part of the compiled expression, charged before allocation, one budget per Evaluation: sound. `MaxWork` including sort comparisons and Resolver calls is right.

**Selection.** Availability conditions, prelude-once, shared work, failure isolation: coherent. But README rule 9 says selection is "unobservable" and the API says "Select is not a guard": when Complete would fail, Select returns a value, so selection *is* observable in the failure case. Qualify rule 9 to success. The `Select` path is a third mini-language (member keys only, arrays yield absent), neither JSON Pointer nor JSONata path; that is acceptable but should be named as such. `ReasonImpure` lumps `$eval`, which is deterministic, with `$random`; the reason is opacity, not impurity. `ReasonUnsupportedCall` encodes planner immaturity as a language property: every standard function except `$random`, `$eval`, and the fixed clock is referentially transparent, so the doc should admit the allowlist is an implementation limitation that will grow, and that `Plan` results are therefore not stable across versions.

**Reads.** Sound and conservative; the array-broadcast rule matches path semantics.

**Environment, clock, timezone, `$eval`.** Clock fixed per Eval/Prepare matches the reference; UTC default matches; `$eval` in-budget is right. Whether `$eval` sees `Env.Bindings` and the enclosing block's bindings is unstated.

**Unmarshal.** The README assigns wire decoding to the binding ("the governing binding specification has decoded the wire"). `Unmarshal` then makes three wire-decoding decisions on its own: duplicate member names rejected (reference: last wins; RFC 8259: SHOULD be unique), number classification, and (presumably) lone-surrogate handling. These are the right decisions for OpenBindings, but they are binding decisions living in the evaluator, and they are undeclared divergences from the reference's input behavior.

**Ledger consistency.** Rows 1, 2, 5, 6 are documentation-over-reference and violate rule 6 as written. Row 7 (`$uppercase`) is a non-divergence and should not be in a ledger of divergences; it also reveals that the host's stdlib does not offer full case mapping, which strains rule 3's "what its host offers". Row 8 (regex) is "pending" on the most consequential question in the file, and its "documentation is silent" claim needs verification against the pinned regex page. Missing rows: string ordering, `Unmarshal` duplicate keys, `$string` notation once fixed, function-valued results.

## What I would change

1. **README: replace the two-tier authority story and rule 6.** Add after "The split": "Authority is resolved in this order: the documentation's normative prose; its examples; an authority it incorporates by reference (`JSON.stringify`, XPath picture strings, regex syntax), read as specifying the algorithm over the abstract value with the incorporating host's value model replaced by the member's; the value model; the reference implementation's behavior at the pinned commit." Rewrite rule 6: "Divergences are declared, never silent. A departure from the reference implementation's observable behavior is permitted only (a) where the documentation specifies otherwise, (b) where the documentation is silent and the value model decides, or (c) where the reference implements something the documentation does not describe. Each is recorded with its class, its reason, and the fixtures it departs from; a departure no fixture exercises is recorded with a fixture the member adds. The reference suite is the detection floor; a member also runs differential tests against the reference over generated inputs." Re-tag every ledger row with its class; delete the `$uppercase` row.

2. **README: pin a class value-model floor and stop calling it the host's.** Replace rule 3 with: "A member represents every integer of at least 64 bits exactly and every finite IEEE 754 binary64 value. A numeric token or literal denotes its exact integer value when spelled as an integer and the nearest binary64 otherwise. Strings are sequences of Unicode scalar values. Comparison, ordering, membership, and `$type` are decided by mathematical or textual value across all representations. A member may exceed this floor; it must not fall below it." Then "no parity between members" becomes "members agree on the floor".

3. **Numbers doc: one exactness rule for every operation.** Replace the `+`/`/` paragraphs with: "An operation whose operands are all exact yields the exact result when it is an integer and otherwise the exact rational result rounded once to float64. An operation with a float64 operand is computed as the exact rational result of its operands' values, rounded once to float64. Refusal (D1001) is reserved for division and remainder by zero, a non-finite result, and an exact result whose bit length exceeds `MaxIntegerBits`." If the authors insist on refusing inexact mixed conversion, then it must be an engine code (`CodeInexact Code = "E1006"`) and it must apply to `/` too. Also add: "`$string` renders a float64 as ECMAScript `Number::toString` specifies: shortest round-trip digits, positional notation for `1e-7 <= |x| < 1e21`, exponent notation otherwise with no zero-padded exponent, `-0` as `0`."

4. **Errors: engine refusals never wear language codes.** `MaxIntegerBits` exceeded is `CodeBudget` like every other `Limits` field. Bytes ordered against a string is either defined (by presentation) or `CodeUnsupportedValue`, not T2010. `Unmarshal` syntax errors get `CodeSyntax`-class handling or a distinct `CodeMalformedInput`. State in the `Code` doc: "A language code is raised only in a situation the documentation or reference defines for it; every refusal this engine adds is an E code, so `Class() == ClassEngine` identifies behavior another member might not share."

5. **Selection: fix the ctx hole and the observability claim.** `func (e *Expression) Prepare(ctx context.Context, input any, env *Env) (*Evaluation, error)`, documented as "classifies the root through the Resolver if it is foreign, charged to the budget". Rename `ReasonImpure` to `ReasonOpaque` ("calls `$random` or `$eval`, whose result the planner cannot relate to a complete evaluation"). Reword README rule 9: "Selective evaluation, if offered, is unobservable in success: whenever a complete evaluation would succeed, a field obtained by evaluating only part of the expression is identical to that field of the complete result. Selection is not a guard; a sibling field's failure is not observed." Rule 7: "closed except for the clock, entropy, and a caller-supplied resolver that presents values, never functions."

## On the concept

The idea underneath is right and the package doc comment proves the authors can execute it: a native engine over host representations, an explicit numeric tower with exact carriage, comparison by value, budgets charged before allocation, a closed environment with one named door, and selection that shares work. That doc comment is the best specification of a JSONata value model I have seen, including the reference's. The README is weaker than the package it introduces. It claims the value model is "the host's" when it is a designed algebra; it claims two authority tiers when there are three; it states a divergence rule its own ledger breaks four times; it claims "refuses rather than approximates" while the package's most carefully argued example is an approximation; and it borrows the regex analogy to argue for cross-host portability, which is precisely what regex engines never achieved. Every one of these is a prose defect, and every one is cheap to fix, but they matter because the README is the *class definition* and a JavaScript member will be written to it. A JS engineer reading "the host defines what a number is" will ship float64-only and be a member in good standing, and the two members will disagree on `=` over a 64-bit ID.

The deeper question is what "documentation as authority" can mean for a language with no specification. My answer: it can mean something, but only as a precedence order over a graph of authorities (prose, examples, incorporated standards, value model, reference), with a stated rule for how incorporated standards are read when they carry a value model of their own, and with the reference suite named as the detection floor rather than smuggled in as the oracle. Without that, the position collapses into "the reference, with overrides we felt strongly about", which is what every port does with less honesty. With it, the position is genuinely better than the field: divergence becomes a classified, cited, fixture-pinned artifact instead of a bug tracker.

The single most valuable thing this repository could do for OpenBindings is not on its list: turn the "portable core" from an observation into a normative specification, small enough to be exhaustively tested, owned by the OpenBindings spec, and require every member to agree on it exactly. That is where contract meaning has to live. Everything outside the core can be "documented JSONata, with declared divergences", and that is an acceptable place for `$formatNumber` picture strings and regex dialects to be. It is not an acceptable place for `=`, `$string`, and integer identity, and today the README puts them there.
