# Iteration-3 panel: JSONata practitioner

Cold read of `b501e30`. Lens: a JSONata practitioner (Node-RED, Step Functions, jsonata-js).

## Grades

| Criterion | Grade | One-line justification |
| --- | --- | --- |
| Idiomatic fit for Go | B+ | `(value, present, err)`, `iter.Seq`, `regexp`-style `Compile`/`MustCompile`, and sentinel `errors.Is` are all right; the map-versus-`*Object` two-arm switch on every object result is the one place a JSONata result is harder to consume than in JS. |
| Ergonomics of the common path | B+ | Compile, Unmarshal, Eval, Marshal is four lines and `EvalJSON` collapses it; but there is no way to evaluate over an absent input (`nil` is null, not undefined), which is the first thing a jsonata-js user does with `expr.evaluate()`. |
| Correctness and footgun risk | B- | Exact integers are the right call, but the mixed-arithmetic rule is keyed to literal spelling (`x / 100` works, `x / 100.0` errors), `[]byte` "is a string" everywhere except ordering, string ordering silently changes from UTF-16 to code point, and the regex dialect is unruled. |
| Performance headroom the API permits | A- | By-reference carriage, no JSON round trip, views over foreign values, `Reads()` for fetch narrowing, and selective evaluation are all things jsonata-js cannot do; `Reason` giving no detail is the only gap. |
| Concept soundness | B | Host-native values are exactly right for this project; "documentation as authority" is hollow where the documentation is a tutorial, and in practice the reference suite plus the ledger is the real authority, so the ledger's honesty and completeness is the whole product. |
| Overall | B+ | I would use this for OpenBindings transforms today and trust its refusals more than jsonata-js's silence; I would not yet trust the ledger to tell me everything that changed. |

## Would my expressions mean the same thing?

1. **`Account.Order.Product.Price`** (path navigation, flattening, unwrapping). Same result, and the numbers come back as carried `json.Number` tokens rather than float64, which is fine because `Marshal` emits them verbatim. Undefined by the doc comments: what `a` returns over `{"a":[1]}`. The reference returns `[1]` (the last-step rule keeps an actual array when exactly one item contributed it) while `a.b` over `[{"b":1}]` returns `1`. The documentation's "singleton array and value equivalence" text does not state that rule; the reference's `evaluateStep` does. The doc comments claim the documentation governs flattening and unwrapping, and this is the first place the documentation does not say enough. Not in the ledger, and it needs to be settled in words because `items` versus `items[0]` versus `items[]` is bread-and-butter JSONata.

2. **`$sum(Account.Order.Product.(Price * Quantity))`**. Same. Small int64 times float64 converts exactly, sums in float64. Becomes different only if a Quantity exceeds 2^53, in which case this errors (D1001) and the reference silently rounds. Declared (row 4).

3. **`$round(Price * 1.075, 2)`** and specifically **`$round(1.005, 2)`**. Different. Reference: `1.01`. Here: `1` (1.005 as float64 is below the midpoint, so half-to-even on the binary value goes down). Declared (row 2), but the declared authority is wrong: the float64 `1.005` is bit-identical in V8 and Go, so "the value model decides" is not true; both hosts hold the same value and the two engines apply different algorithms to it. The documentation's `$round` examples are all decimal (`$round(123.456, 2)` is `123.46`), which is at least as much a statement about basis as silence. This is the divergence a Node-RED user will actually hit, more than `0.1 + 0.2`.

4. **`{"id": id}` with body `{"id": 9007199254740993}`**. Different, and this library is the one that is right. Reference emits `9007199254740992`. Here `9007199254740993`. Declared (row 3). But the sibling **`id = 9007199254740993.0`** flips: reference `true` (both sides collapsed to 2^53), here `false` (float64 9007199254740992 versus exact int64 9007199254740993). JSONata has one number type and `1.0 = 1` is documented as true; a `.0` suffix changing a comparison is spelling sensitivity the language does not have. Not declared as such.

5. **`total_cents / 100`** and **`total_cents / 100.0`** with `total_cents = 1758000000000000123`. The first works (exact quotient rounded once to float64). The second is an error (D1001) because `100.0` is a float64 literal and the integer cannot convert exactly. Same for `total_cents * 0.01`. No JSONata user distinguishes `100` from `100.0`; the doc comment's own example (`9007199254740993 + 0.5 fails while 0.1 + 0.2 yields`) admits this. Row 4 declares "mixed integer and float arithmetic beyond 2^53" but nobody reading that row would predict that `/ 100.0` is "mixed" and `/ 100` is not.

6. **`"Total: " & (1.1 * 3)`** (message building in Node-RED). Different. Reference `"Total: 3.3"`. Here `"Total: 3.3000000000000003"`. Declared (row 1). What is not declared: the notation threshold. "Shortest decimal that round-trips" picks the digits, not the format. `JSON.stringify(1e20)` is `"100000000000000000000"` and `JSON.stringify(1e21)` is `"1e+21"`; Go's `strconv.FormatFloat(x, 'g', -1, 64)` renders `1e6` as `"1e+06"`. If the implementation uses `encoding/json`'s float formatting it matches ECMAScript; if it uses `'g'` it does not, and `$string(2.5e6)` becomes `"2.5e+06"`. The doc comment must pin the notation, not just the digits.

7. **`$keys($)` over `{"10":1,"2":2,"b":3,"a":4}`**. Different, three ways. Reference `["2","10","b","a"]`. Here via `Unmarshal`: `["10","2","b","a"]`. Here via a `map[string]any` input: `["10","2","a","b"]`. Declared (row 5) for the integer-like hoisting; the map path reorders every key, not just integer-like ones, and the ledger does not say that. Same applies to `$each`, `$spread`, `$merge`, `$string($)`, and the transform operator over map input.

8. **`$split("👍🏽a", "")`**. Different. Reference: five UTF-16 code units. Here: `["👍","🏽","a"]`. Declared (row 6). Gain.

9. **`$sort(["～", "😀"])`** and **`"～" < "😀"`**. Different, undeclared. Reference orders by UTF-16 code unit, so `😀` (D83D DE00) sorts before `～` (FF5E): `["😀","～"]`, and the comparison is `false`. Here by code point (1F600 > FF5E): `["～","😀"]`, `true`. Row 6 covers `$split` and `$match.index` but not `<`, `$sort`, or `^()`. Any transform that sorts user-supplied names with emoji changes order.

10. **`$match(css, /(\d+)(?=px)/)`** and **`$replace(s, /(\w+) \1/, "$1")`**. Undefined. The ledger says "pending ruling". If the dialect is Go's RE2, both fail at `Compile` and the reference runs them. This is the single largest practical loss for anyone bringing expressions over and it is the one row with no answer.

11. **`$now()` and `$millis()` in the same expression**. Same: both engines fix the timestamp once per evaluation. Selective evaluation keeps that property, which is the right design.

12. **`$power(2, 64)`**. Different, undeclared. Reference `18446744073709552000` (float). Here the exact `*big.Int` `18446744073709551616`. `$power(10, 400)` errors in the reference (non-finite) and succeeds here. Row 3 sort of implies this; it should be its own row because `$power` is where the integer domain most visibly outruns float64.

## What a JSONata user gains and loses

**Versus jsonata-js:**

Gained: exact integers, which is the reason this project exists; `9007199254740993` survives `Unmarshal`, `$string`, `+ 1`, `$formatNumber` (presumably; unstated), and `Marshal`. Refusal instead of rounding when an exact integer meets a fraction. Real `undefined` on the API surface (`present`), instead of JS `undefined` that turns into a missing key or `null` depending on which serializer you hand it to. First-class bounds (`Limits`) and cancellation; jsonata-js's timebox is a test utility hidden behind `timeboxExpression`. Code points everywhere instead of the UTF-16 leaks in `$split("")` and `$match.index`. `$string` of floats that says what the float is. Selective evaluation and `Reads()`, which do not exist anywhere in the JSONata ecosystem. Bytes as a first-class value with a declared boundary encoding rather than whatever `Buffer` did. Error offsets in bytes with line and column. Compile-time regex validation. A closed environment that cannot be talked into `$env` or `require`.

Lost: `registerFunction` and every host function a Node-RED or Step Functions user leans on (`$env`, `$flowContext`, `$moment`, `$clone`, `States.*` are all gone; only values bind). Lookaround and backreferences if the regex ruling lands on RE2. `$round` that matches what a human expects on decimal midpoints. `"0.3"` instead of `"0.30000000000000004"` in message strings (the reference's 15-digit rendering is a departure from its own documentation, but it is the behavior people have calibrated to). Insertion-ordered keys when the input is a Go map. Evaluating over an absent input. Duplicate JSON member names in input (`Unmarshal` rejects them; `JSON.parse` takes the last, and upstream APIs do emit them). The 1e7 range cap with its own code (D2014) becomes a generic budget error (E1002), so a transform author cannot distinguish "your range was too big" from "your output was too big".

**Versus a faithful port:**

A faithful port would carry every one of the reference's JS artifacts into Go: numbers as float64 (which would corrupt the IDs this project handles), key hoisting, UTF-16 index math, 15-digit rendering, decimal-spelling `$round`, and the 1e7 range cap. It would agree with jsonata-js on every fixture and give the wrong answer for `9007199254740993`. For OpenBindings, the host-native member wins outright. For a general-purpose Go JSONata used to migrate Node-RED flows, a faithful port wins, because those users have thousands of expressions calibrated to the reference's quirks and nobody is going to read a ledger. This library should say which of those it is; the README says "class", the doc comments say "over Go values", and the honest answer is "the OpenBindings evaluator, usable elsewhere if you accept the ledger."

## What I would change

1. **Make mixed arithmetic value-based, not spelling-based.** Replace the sentence "An integer operand combined with a float64 operand must convert to float64 exactly, and is an error (D1001) otherwise" with: "A float64 operand whose value is integral and within ±2^53 participates in arithmetic and comparison as that integer, so `x / 100.0` is `x / 100` and `x * 1.0` is `x`. Otherwise an integer operand must convert to float64 exactly, and is an error (D1001) when it cannot, so `9007199254740993 + 0.5` fails while `0.1 + 0.2` yields the float64 sum." Apply the same rule to numeric literals so `9007199254740993.0 = 9007199254740993` is true. The ±2^53 bound keeps `1e23` a float and prevents its binary expansion (`99999999999999991611392`) from leaking into integer results.

2. **Round on the decimal spelling and delete ledger row 2.** Replace the `$round` paragraph with: "$round(x, p) rounds the shortest round-trip decimal rendering of x half to even at p places and parses the result, so `$round(2.675, 2)` is `2.68` and `$round(1.005, 2)` is `1.01`, as the documentation's decimal examples show; the float64 value is identical in every host, so this is an algorithm, not a value-model choice." The current ledger justification ("the value model decides") is false on its face and a reviewer of the ledger will notice.

3. **Rule on the regex dialect now and declare the loss concretely.** Row 8 cannot ship as "pending". Proposed wording for the doc comment: "Regex literals and the pattern arguments of `$match`, `$replace`, `$split`, and `$contains` use RE2 syntax as Go's regexp package defines it, with flags `i` and `m` as the documentation lists. Lookahead, lookbehind, backreferences (`\1`), and possessive quantifiers are not supported and fail at Compile (S0302); `(?<name>...)` is accepted. An empty match advances one code point." And the ledger row: "Regular-expression dialect | JavaScript: lookaround and backreferences | RE2: refused at Compile | the documentation is silent; fixtures using those constructs are declared." Then count the fixtures.

4. **Correct the README's portable-core claim and fill the ledger.** "That subset is exactly the part of the language where the documentation and the reference agree without exception" is false: `$string` (floats, integer-like keys), `$keys`, `$merge` (member order), and `$sift` (order) are in the listed subset and in the ledger. Reword: "Authors who stay inside it, over string, boolean, null, and integer values, and objects without integer-like keys, get identical results from every member." Add ledger rows for: string ordering by code point versus UTF-16 unit (`<`, `$sort`, `^()`); `Unmarshal` rejecting duplicate member names; `$power` exact beyond 2^53 and finite beyond float64; the range cap surfacing as E1002 rather than D2014. And pin `$string` notation in the doc comment: "in ECMAScript Number::toString form, exponent notation only at magnitude ≥ 1e21 or < 1e-6."

5. **Make `[]byte` a string for ordering too, or for nothing.** "A []byte is a string for $type, $length, $contains, and every string function" followed by "ordering a []byte against a string is an error (T2010)" is a contradiction: T2010's own text says the operands must be numbers or strings, and you just said it is one. Replace with: "A []byte compares and orders as its encoded string against strings and against other []byte values, so `$sort` over a mixed array is total; equality between two []byte values is by bytes, which agrees with equality of their encodings." If encoding on every comparison is unacceptable, then say a []byte is not a string for `$type` either and let `$type` return `"bytes"`, but pick one.

## Things the doc comments leave unclear to a JSONata user

- What `a` returns over `{"a":[1]}` (`[1]` or `1`), and whether the `[]` keep-array suffix (`a[]`) is honored; the last-step single-array rule is reference behavior the documentation does not state.
- Whether `nil` input can ever mean absent; `$exists($)`, `$type($)`, and `{"x": $}` all differ between null and undefined, and jsonata-js users evaluate with no input routinely.
- The regex dialect, and with it: lookaround, backreferences, named-group syntax, which flags are accepted, empty-match progression, and whether the reference's D1004 ("matches zero length string") exists.
- `$replace`: whether `$0` is the whole match; how `$10` resolves with fewer than ten groups (the reference falls back to `$1` followed by `0`); whether the function-replacement form and the `limit` argument are supported; what the match object's `index` and `groups` look like as Go values.
- The exponent-notation threshold for `$string` of a float64 (`1e20`, `1e-7`), and whether `$string(json.Number("1.0"))` is `"1"` (classified to float64) while `Marshal` of the same carried value emits `1.0`.
- Whether `$floor`, `$ceil`, `$round` of a float64 return float64 or enter the integer domain; `$floor(1e23)` as a `*big.Int` would expose `99999999999999991611392`.
- `$formatNumber`, `$formatInteger`, `$formatBase`, `$parseInteger`: not mentioned at all. What decimal digits does `$formatNumber` operate on for a float64, what does it do with a `*big.Int`, and does it round half-even per XPath F&O?
- The transform operator: is the deep copy an `*Object` tree, are untouched subtrees carried or copied, and is the copy of a `map[string]any` reordered?
- `$base64encode` of a `[]byte` (double encoding under the "used as a string" rule?) and `$base64decode` yielding non-UTF-8 (error, or replacement characters as the reference's `Buffer` gives?).
- `$boolean([]byte{})`, and `$boolean` of a nil slice or nil map.
- The range operator: is `[1..1e6]` accepted (float64 with integral value), what is the cap, and which code.
- `$number`: hex/octal/binary prefixes, whitespace, `"1e400"`, and whether `$number("9007199254740993")` is exact int64.
- `$eval`: which environment it sees (does it observe `Env.Bindings` and the enclosing lambda scope?), and whether its result is subject to the same carriage rules.
- Which functions the planner has "qualified as selectable"; `ReasonUnsupportedCall` names no function and no offset.
- `$toMillis` return type, and `$fromMillis` with a float64 argument.
- Which error codes are "defined by the documentation"; I do not recall the documentation cataloguing codes, they live in the reference's messages table, so the package is borrowing implementation vocabulary while claiming documentation authority.
- `$sort` stability guarantee, and comparator behavior on `[]byte` versus `*big.Int` versus float64 mixes.
- Whether `[]uint8` from a Go caller is bytes or an array of small integers (it is `[]byte`, and the admitted-values list should say so explicitly).
- `Unmarshal` of `-0` and `-0.0`, and whether `$string(-0.0)` is `"0"` because the value is classified or because the renderer special-cases it.

## On the concept

The regex analogy is the right analogy, and it should worry the authors more than it comforts them. Go's `regexp` is native and well designed, and every engineer who moved a regex from JavaScript to Go has hit "backreferences are not supported" and "lookbehind is not supported" in production. Go answered that by declaring, in one paragraph, exactly what it does not do, and the ecosystem adjusted. That is the precedent being invoked: it says the divergences will be real, users will hit them, and the only thing that makes it tolerable is a declaration that is complete, blunt, and stable. The ledger is that declaration, and today it has eight rows, one of which is "pending", and I found four undeclared divergences reading a stub. When the reference suite actually runs, the ledger is what I will judge, not the README.

"Documentation as authority" is a framing I trust in exactly the places where the JSONata documentation is a specification, and distrust where it is a tutorial. It is a specification for `1/2 = 0.5`, for undefined propagation, for `$string` calling `JSON.stringify`, for what characters are. It is a tutorial for the singleton rules, silent on the regex dialect, silent on rounding basis, silent on error codes, and it never says what a number is. In every one of those silences the package has to choose, and where it chose the reference's behavior (error codes, most of the suite) it is a port in all but name, and where it chose Go's behavior (rounding, regex) it is a divergence with a thin justification. That is fine. What is not fine is dressing "we followed the reference here and Go there" as "we followed the documentation": the ledger should just say, per row, "documentation", "reference", or "host", and let the reader decide whether they agree.

Would I rather have a faithful port? For OpenBindings, no. The project exists to carry an int64 ID through a transform without it becoming `...992`, and a faithful port of jsonata-js would corrupt it at `JSON.parse` before the language even ran; the reference's own value model is the bug. Host-native values with exact carriage and refusal over approximation is the correct stance for this use, and `(value, present, err)` plus `Limits` plus selective evaluation gives me an API I would actually rather have than jsonata-js's. For a general Go JSONata aimed at Node-RED migrants, I would want the faithful port, because those users will never read a ledger and have thousands of expressions tuned to `$round(2.675, 2) = 2.68`. The README should say plainly that this class is the former, and the "portable core" should be the honest contract it promises to be, which means the claim about it has to be true.
