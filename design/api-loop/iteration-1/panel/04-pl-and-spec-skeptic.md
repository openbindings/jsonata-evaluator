## Attacking the concept

### (1) Documentation as authority

Steelman: the reference implementation is a program, not a spec; treating it as the authority freezes its bugs, its JS number type, and its property-ordering quirks into the language. Documentation is written in language-level terms ("the result is a sequence", "undefined is not null"), which is the right level to conform to. Pinning a commit makes it stable. Where the reference departs from the docs, someone has to say which is the language, and "the prose the maintainers wrote to describe intent" is a defensible pick.

The attack has three prongs.

First, the README does not actually operate on this authority. Rule 1 says membership is "verified against the reference test suite for that version". The reference suite was generated by and for the reference implementation; it encodes every one of the reference's "departures from its own documentation" as an expected value. Rule 6 then permits a departure from that suite "only where the value model cannot represent a reference value". Put together: wherever the reference departs from the documentation in a matter of *behavior* (path semantics, function semantics, error selection, anything not about numeric or string representation), the member is required to follow the reference, because the fixture is authoritative and the value model can represent the fixture's expected value. So "the documentation wins where it speaks" is true only inside the value-model quadrant. Outside it, this class is a port of the reference's behavior with a different number type, which is exactly what the README says it is not.

Second, "silence" is not a decidable predicate on prose. The docs are tutorial-shaped: examples, a function reference, a few pages of semantics. Whether the docs "speak" on a point is a judgement call, and the entity making the call is the implementer. So "documentation is the authority" cashes out as "our reading of the documentation is the authority", with no adjudication procedure. A PL person will ask: when two members read the docs differently, who decides? The README's answer is "the project's members aligning with each other is a quality commitment of the project", which is to say, the project decides, which is to say, the implementation decides.

Third, the documentation incorporates other authorities by reference, and one of them is JavaScript. The regex page defines regex literals in terms of JavaScript regular expressions (verify the pinned commit, but that is how I remember it); `$formatNumber`, `$formatInteger` and `$fromMillis` are defined by reference to XPath Functions and Operators 3.1 picture strings; `$string` is described in terms of JSON serialization. The moment the doc says "as JavaScript does", documentation-as-authority becomes reference-as-authority by transitivity, and a host-native Go member either embeds a JS-compatible regex engine (a port of exactly the kind the README disclaims) or declares a dialect divergence that rule 6 does not permit, because the divergence is not about a value the model cannot represent.

Does it land? Yes, on all three prongs, but it is repairable. The fix is honesty, not a different authority: the operational authority is the pinned suite plus a ledger; the documentation adjudicates fixtures the ledger challenges; and the incorporated authorities (JS regex, XPath F&O) are named and each given an explicit treatment.

### (2) Host-native value model

Steelman: JSONata has no number type; JS's double is an accident of the reference. A Go program holding `int64` or `json.Number` should not lose precision by passing through an expression that only selects. Carriage-exactness (rule 4) is a real, valuable property that no port offers. And JSON itself (RFC 8259) declines to define numeric precision, so a host-defined model is the same stance JSON takes.

The attack: this language is being used to move values *between* systems, and the person who writes the transform is not the person who chooses the host. An interface document is published by a service; its transforms are evaluated by whichever consumer picks it up, in Go, TS, or a member that does not exist yet. The README says "two members agree wherever their value models agree. Where the models differ, the members differ, and that is correct." From the author's side, that sentence reads: "the meaning of your transform is a function of a variable you do not control". That is not a value model, it is the absence of one, dressed as pluralism.

RFC 8259 is the wrong precedent because JSON's answer is not "the host decides"; it is "interoperability is guaranteed only within IEEE double, and implementations that go beyond it do so at their own risk". That is a *profile*, and it is what the README's "portable core" gestures at while explicitly refusing to make it a rule.

The concrete consequences are not hypothetical. Under this package's doc: `9007199254740993 + 0.5` is an error in Go and a value in the reference; `9223372036854775807 + 1` is an error in Go and a value in the reference; `$string(9007199254740993)` is `"9007199254740993"` in Go and `"9007199254740992"` in the reference; `$keys({"b":1,"2":1,"a":1,"1":1})` is `["b","2","a","1"]` over an `*Object` in Go, `["1","2","a","b"]` over a map in Go, and `["1","2","b","a"]` in the reference (JS orders integer-like keys first). `$keys` and `$string` are both in the README's "portable core", which claims that subset is "exactly the part of the language where the documentation and the reference agree without exception". It is not; the exceptions are large integers and integer-like keys, both of which appear in real payloads.

Does it land? Partly. Carriage-exactness is worth having and the attack does not touch it. What lands is: a host-defined *arithmetic* model without a normative portable profile is an abdication for a cross-system language. The README needs to stop calling the portable core "an observation, not a rule".

### (3) The regex analogy

Steelman: the analogy is not "regex is portable"; it is "regex engines are written natively, declare what they don't do, and nobody ports PCRE". On that reading it justifies exactly three things: write it native, use host strings, declare gaps.

The attack: the regex world is the cautionary tale, not the model. There is no shared regex notation; there are PCRE, RE2, ECMA-262, POSIX ERE, and they disagree on syntax (backreferences, lookaround), on semantics (leftmost-longest vs leftmost-first), and on what a character is (UTF-16 code unit vs code point vs byte). Every cross-system use of regex, JSON Schema `pattern` being the closest cousin to an OpenBindings transform, has had to pin a dialect ("ECMA 262") and has *still* produced a decade of interop bugs because hosts implement the pinned dialect with their native engine. Go `regexp` does not claim to implement "regex"; it documents RE2 syntax and refuses everything else at compile time. Taken seriously, the analogy predicts dialects, which is precisely what OpenBindings pinned a documentation commit to prevent.

The analogy also fails on the axis that matters. A regex lives in the program that runs it: one author, one host. A transform lives in a published document: one author, N hosts. And a regex's output is a boolean or spans; a transform's output is the value that flows onward into the caller's business logic. Divergence in a match is a bug; divergence in a transformed value is data corruption.

Finally, regex borrows credibility from a founded notation (regular languages, or at least a precise backtracking model with decades of literature) and lends it to a language with no semantics at all. The analogy is decorative where it is comforting and load-bearing where it is dangerous: it is used to justify "the host defines what a number is", and that is the one place it is wrong.

Does it land? Yes. Keep the analogy for "written native, not ported"; drop it as an argument for host-defined arithmetic.

### (4) Declared divergence as sufficient discipline

Steelman: silent divergence is the actual enemy; a ledger pinned to fixtures, invalidated when the fixture changes, is a real mechanism, better than anything the existing ports have.

The attack, in four parts. (a) A ledger is retrospective and fixture-shaped: it records where the member disagrees with tests that happen to exist. Divergence on an expression no fixture covers is silent by construction. The suite is large but it is not a semantics; it does not cover integer-like key ordering, code-point vs code-unit string ordering, or `int64` overflow, so those divergences are silent under this discipline while being fully known to the authors. (b) A consumer cannot use a ledger to predict behavior for *their* expression without knowing which divergent paths it touches; the ledger is a changelog, not a contract. (c) Rule 6's permission clause, "only where the value model cannot represent a reference value", is vacuous for Go: every reference value is a JS value, every JS value is a `float64` or string or bool or null or a structure of those, and Go represents all of them. The Go member's `int64` exactness, `*big.Int` literals and every refusal in the numbers section are not cases where the model *cannot represent* the reference value; they are cases where the model *chooses a different one*. As written, the Go member is not a member of its own class. (d) Regex dialect and picture-string divergences are not value-model divergences at all, so rule 6 has no category for them.

Does it land? Yes. "Declared, never silent" is the right slogan; the rule that implements it has the wrong predicate.

### (5) Choosing JSONata at all

Steelman: interface authors need object and array constructors, `$merge`, `$sift`, conditionals, and a real standard library; JSONata reads well, has a pinned doc, and is already ratified in the OpenBindings spec. JMESPath lacks lambdas and had no arithmetic until recently; jq has the same reference-vs-docs problem and worse portability (gojq diverges); CEL is designed for predicates and policy, and constructing output shapes in it is clumsy.

The attack: look at what the Go member's numbers section actually specifies. Exact `int64`, separate `double`, overflow is an error, non-finite is an error, no silent promotion, comparison by mathematical value, a closed environment, bounded evaluation, no host functions by default. That is CEL's value model, nearly clause for clause. CEL has a written spec, a typed checker, a conformance test suite that multiple independent implementations (Go, C++, Java) pass, and it was designed for precisely this deployment shape: untrusted expressions authored in one place and evaluated on arbitrary hosts. The project is reconstructing CEL's semantics inside a language that has none, and then calling the documentation the authority for semantics the documentation does not contain.

Does it land? Not as a re-litigation; the spec ruling is settled and the authoring ergonomics argument for JSONata is real. It lands as a diagnosis: the reason the Go member has to write a five-paragraph numeric semantics is that the language has none, and the cost of that gap is paid by every member and every author forever. The remedy short of switching languages is to write down the numeric semantics once, at the class level, as a normative profile, so the TS member and a future third-party member implement the *same* arithmetic rather than each host's.

## What a PL person would want instead

Ranked by value per effort:

1. **Fix the authority statement and rules 6, 8, 9 to say what is actually enforced.** State: the pinned reference suite is the operational authority; the documentation adjudicates a fixture the ledger challenges; a divergence is permitted where the member's stated value model yields a different value or refuses, and where an incorporated sub-authority (JS regex, XPath F&O) cannot be honored natively. Half a day; removes every internal contradiction below.

2. **Promote the "portable core" to a normative profile, in the OpenBindings spec, not the evaluator README.** A grammar subset, a library subset, a numeric domain (integers exact within the IEEE safe range, doubles otherwise, no silent overflow), an object-ordering rule (insertion order is not observable in the profile, or is observable and defined), and a string-character rule (code points). Every member must pass the profile fixtures with an empty ledger. Authors who stay inside get identical results everywhere; the promise the README makes informally becomes a contract. A week of spec work plus fixtures; the highest interop value of anything on this list.

3. **A class-level value-model spec, shared by all project members.** The package comment's Numbers and Strings sections are already 80% of it. Move it up a level, make the TS member implement it (TS can do `int64` via BigInt and the same refusal rules), and the "no parity between members" clause becomes "parity by construction among project members". A few days.

4. **Differential testing and properties.** A fuzzer over the portable core against jsonata-js at the pinned commit, and property tests for the invariants the API claims: exact carriage, comparison-by-value across representations, `Select(p) == field(Complete(), p)` whenever `Complete` succeeds, `Reads()` soundness. Two weeks; catches the silent divergences the ledger cannot.

5. **A formal semantics of full JSONata.** Correct in principle, no one will adopt it, and the language's sequence/flattening/singleton rules would take months to formalize faithfully. Low value per effort.

6. **Switch to CEL.** Highest rigor, but it re-opens a settled ruling and loses the authoring ergonomics that motivated JSONata. Note it, do not do it.

## Semantic commitments in the API

**Absence.** `(value, present, err)`; present nil is null; `WithBindings` nil is null; `Access.Get` ok==false is absence. Sound and consistent. Undefined: whether an unbound variable is absent (it is in the language; the doc should say `WithBindings` omission is the way to bind absence). Complete otherwise.

**Ordering of object members.** Maps sorted, `*Object` insertion. Sorted by what is not stated at the point of commitment (presumably byte order, which equals code-point order for valid UTF-8; say so). The commitment is internally consistent but it contradicts README rule 5's spirit ("never by host type"): the same logical document decoded by `encoding/json` versus `text.Decode` yields different `$keys`, `$string`, `$merge` and `$each` results. And neither matches the reference's integer-keys-first order, which the docs do not state and which the ledger will not catch without a fixture. Undefined: the ordering of keys of an object produced by `$merge` of a map and an `*Object`, and whether object equality is order-insensitive (the reference's deep-equal is; the doc should commit).

**Carriage and identity.** "Same type, same identity" for a value only selected, copied, or rearranged. The language does not define which operations are "pure copies": JSONata path navigation builds result sequences, flattens one level, and unwraps singletons, and whether `a.b` over a single `a` with array-valued `b` returns the carried slice or a fresh flattened one is an implementation detail of the reference, not a documented fact. The API is committing to a distinction the authority does not draw. Either enumerate the carrying forms (`$`, `$$`, a simple member path with no flattening, a bound variable, `$lookup`) or weaken to "may alias".

**Ownership.** "Constructed values are owned by the caller" and "a field selected twice is computed once, and a later Complete reuses every field already selected" cannot both hold: the memoized `*Object` from `Select("a")` is the same pointer inside `Complete()`'s result, and `Object` is not safe for concurrent mutation while `Evaluation` is safe for concurrent use. Also a constructed `*Object` may hold carried leaves, so ownership is of the shell only. Commit to "values returned from an Evaluation are read-only until Close" or copy on return.

**Numbers on output.** `int64`, `float64`, `*big.Int`; result type depends on runtime values (`4/2` is `int64`, `5/2` is `float64`). Acceptable behind `any`. The refusal rules are the problem: (a) `int64 + int64` overflow is refused even though `*big.Int` is in the result set and the exact result is representable; "never a promotion" makes the numeric domain not closed under addition while admitting literals beyond `int64`, which is arbitrary. (b) "An integer operand which is not exactly representable as `float64` is refused" tests the *operand*, not the *result*: `9007199254740993 / 2` has an exactly representable `float64` result and is refused anyway. Rule 8 says refuse rather than approximate; it does not say refuse representable results. (c) Rule 8 is violated by admission itself: `json.Number("0.1")` becomes a rounded `float64`, `"1e-400"` silently becomes `0`. Scope rule 8 to arithmetic results and non-finite classification, or it is unsatisfiable. (d) `int64` min divided by `-1` in Go yields min (Go defines it as overflow without panic) and must be caught as D1001; `1 % 0` with "Go's %" panics; commit to D1001 for integer division and modulo by zero explicitly.

**Comparison.** By mathematical value across representations, exact operands never routed through `float64`. Sound and the best clause in the file. Undefined: `int64` versus `float64` where the float is not integral (fine, by value), ordering of `[]byte` against `[]byte` and against strings for `<` and `$sort` (equality is specified, ordering is not), and object equality (see above).

**Strings.** Code points, code-point ordering, simple case mapping. Consistent with `Position` in characters. Undefined: invalid UTF-8 in a Go string. Rule 8 suggests refusal; Go's `range` suggests U+FFFD per byte; the doc must pick, because `$length` and `$substring` differ under the two.

**Bytes.** `$type` is "string", equality with a string is by encoded form, `[]byte` to `[]byte` by bytes, encoding chosen by option. Consistent (base64 is injective, so `a = b` and `a = $string(b)` agree). Two gaps: `text.Evaluate` encodes carried `[]byte` with `base64.StdEncoding` regardless of `WithBytesEncoding`, so `$.blob` and `$string($.blob)` render differently under a non-default encoding in the same call; and the meaning of an expression over bytes depends on an `EvalOption`, so the value model is parameterized per evaluation, which is fine but should be said next to "the environment is closed".

**`*Object` versus `map[string]any`.** Output type encodes provenance (carried versus constructed), which no consumer wants to know. `Object.Map()` not converting nested values means there is no one-call way to a uniform tree. `Object.UnmarshalJSON` is silent about duplicate keys while `text.Decode` rejects them and `encoding/json` maps take last-wins: three admission behaviors for one document within one host.

**`Access`.** `Kind` then typed getters; `Number` exact-or-error is right. No method except `Number` can fail, yet `Reads()` explicitly invites lazy fetching, which fails. Either every method returns `error` or the doc defines a panic-and-recover protocol. `Range` "in order" delegates order to the host, which is coherent with the map/`*Object` split but should be stated as the object's member order for every order-observing operation.

**Selection.** The doc comment is more honest than README rule 9: "when Complete would fail, Select may still succeed" is an observable difference, and `MaxWork` makes it routine (a single field costs less than the whole). State rule 9 as a one-way implication: if `Complete` yields a value, every `Select` equals its field. Undefined: `Select("a")` over a `ReasonArrayInput` result, where "field of an array" is either JSONata's map-over-elements or a structural miss; and whether `$now` under plain `Eval` is fixed per call.

**`Reads()`.** Paths are member-key sequences, but JSONata paths traverse arrays implicitly, so `["a","b"]` means "b of every element of a" and the doc should say so. It also does not say whether the list is *sound* (nothing outside it is read) or merely *indicative*; lazy fetch requires soundness. `$`, `$$`, `*`, `**`, `$lookup`, `$keys`, `$eval` must force `known == false`; say which.

**Errors.** Language codes and engine codes in one string field is fine. D1001 reused for `int64` overflow is a reasonable extension of "number out of range". Undefined: which code an unsupported regex construct raises at `Compile`, and there is no engine code for "incorporated sub-authority not honored".

**Environment.** "No expression can reach host state" is false by the package's own account: `$now`, `$millis`, `$random` read the clock and entropy, and `Access` executes host code under expression control. Say "closed except the clock, entropy, and the supplied Access".

## What I would change

1. **Rewrite rules 6, 8 and 9 in the README.** Rule 6: "A departure from the reference suite is permitted where the member's stated value model yields a different value or a refusal for the fixture's input, or where a sub-language the documentation defines by reference to another authority (regular expressions, XPath picture strings) cannot be honored by the host's native facility. Each departure is recorded with its reason and pinned to the fixture." Rule 8: "An arithmetic result that overflows the stated model or is non-finite is a failure. Admission of a decimal token to a binary type rounds as the model specifies." Rule 9: "If complete evaluation yields a value, every field obtained by selective evaluation equals the same field of that value."

2. **Close the numeric domain and refuse on results, not operands.** Package doc: "Integer with integer yields `int64` when the result fits and `*big.Int` otherwise. Any `float64` operand yields `float64`; an operation is refused (D1001) when its exact result is not representable as `float64` or is not finite. Integer division or modulo by zero is D1001." If you would rather not promote, remove `*big.Int` from the result set entirely and refuse `uint64` and big literals at admission; the current middle position is not defensible.

3. **Name the incorporated sub-authorities in the package doc and give them a code.** Add a section: "Regular expressions are compiled by Go's `regexp` (RE2 syntax). Constructs the documentation admits that RE2 does not (backreferences, lookaround) fail at Compile with `CodeUnsupportedSyntax`. Picture strings for `$formatNumber`, `$formatInteger` and `$fromMillis` implement XPath F&O 3.1 as the documentation incorporates it." And add `CodeUnsupportedSyntax = "E1004"`.

4. **Give `Access` an error channel.** `Get(v any, key string) (value any, ok bool, err error)`, `Range(v any, fn func(key string, value any) bool) error`, `Len(v any) (int, error)`, `Index(v any, i int) (value any, ok bool, err error)`, `String`, `Bool`, `Bytes` likewise. An `Access` error surfaces as `CodeUnsupportedValue` wrapping the cause. This is the price of advertising lazy fetch in `Reads()`.

5. **Make the portable profile normative and put it in the spec, not here.** Replace "An observation, not a rule" with: "The OpenBindings specification defines a portable profile of JSONata 2.1 (grammar subset, library subset, integers exact within the IEEE safe range, code-point strings, member order not observable). Every member passes the profile fixtures with no declared divergence. Outside the profile a member owes documented behavior, which may include a declared divergence." Then make `$keys` ordering and `$string` of large integers either inside the profile with a defined answer or outside it.

## On the concept

The kernel is sound and worth keeping: write the evaluator natively, admit the host's values by reference, carry what you only select exactly, compare by value not by representation, close the environment, bound everything, and refuse rather than round. No existing JSONata port offers that set, and the Go API expresses it cleanly. The `(value, present, err)` triple, the compile-once and prepare-select shape, the by-value comparison clause, and the refusal-over-approximation stance are all things a PL person would endorse.

What is not sound is the authority story wrapped around that kernel. The README says documentation governs, but rule 1 makes the reference suite the thing actually enforced and rule 6 forbids departing from it except in a case that, for Go, never arises. It says the host defines what a number is, but the language is used to publish transforms to hosts the author never sees, and the README's own "portable core" list contains functions whose results differ between the members it describes. It leans on the regex analogy, which, examined, is the history of what goes wrong when a notation is pinned by prose and implemented per host. And it does not notice that the documentation incorporates JavaScript regex and XPath picture strings by reference, so "the host defines what a character is" is going to collide with "the documentation defines what `/(a)\1/` means" on the first fixture that uses a backreference.

Verdict: not a well-argued mistake, a well-built engine with a misdescribed contract. The fix is to say what is actually true (suite plus ledger is the operational authority, the documentation adjudicates, incorporated sub-authorities are named), to close the numeric domain so the refusal rules follow from one principle instead of three, and to move the portable profile from an observation in this README to a rule in the OpenBindings spec where the interop promise belongs. Do those and the "host-native" stance becomes a fidelity feature layered on a portable contract rather than a substitute for one.
