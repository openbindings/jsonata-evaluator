# Iteration-6 panel: programming-language and specification skeptic

Cold read of `81e3693`. Lens: attack the concept; then audit the semantic commitments as laws. The reviewer verified two host facts before writing: Go's `strings.ToUpper("straße")` is `"STRAßE"` (simple mapping only), and Go's shortest formatting of the float64 `1e23` is `"100000000000000000000000"`, so for that single value the host, the reference, and this package would print three different strings.

## Grades

## Attacking the concept

### (1) Documentation as authority

**Steelman.** JSONata has no spec, so something must be authority. The reference implementation is an accident of JavaScript (binary64, UTF-16, own-property order); its test suite encodes those accidents. The documentation is the only artifact that describes the *language* rather than one *program*, it is versioned, it is what OpenBindings pins, and it is what authors actually read. Choosing it is choosing the intent over the artifact, and it forces every departure from the artifact to be argued in writing.

**The attack.** Look at what the class actually does operationally. Membership rule 1 says a member is "verified against the reference test suite". Rule 6 says divergences are "a departure from the reference suite". So the oracle is the suite; the documentation is invoked only to *justify a departure* from it. That is not documentation-as-authority; it is suite-as-authority with documented grounds for appeal. The README's headline claim ("This class takes the documentation as the authority") describes the appeals procedure, not the trial.

Second, the documentation is a tutorial with examples, not a specification. It is silent on evaluation order, on the group-by semantics of object constructors over empty input, on `$replace`'s overflow rule for `$12` with one group, on what `$fromMillis` does with a fraction, on `??`'s treatment of null. The README's split has exactly two regions (documentation speaks; value model decides) and says nothing about the third and largest region: documentation silent, value model not implicated. In every such case `jsonata.go` quietly adopts the reference ("as the reference does", "as in the reference implementation", "follows the documentation and the reference") and does not call that a divergence. So there is an unstated fourth authority, the reference, and it is the default. That is defensible; it is not what the README says.

Third, incorporation by reference smuggles in a value model. The docs define `$string` via `JSON.stringify`, which is defined over ECMAScript Numbers, which are binary64. Ledger row 1 accepts that incorporation (`0.30000000000000004`); ledger row 2 overrides it for `1e21` on the ground that "these values are integers here". But the float64 `1e21` *is* a binary64 value; `JSON.stringify` speaks for it precisely; the README's own rule is "the documentation wins where it speaks". Row 2 is the value model overriding the documentation on a value squarely inside the incorporated authority's domain. The ledger's preamble even has a rule for this ("an incorporated authority speaks only for its own value domain") that the README lacks, and row 2 does not satisfy it.

Fourth, there is no rule for a self-contradictory documentation, or for a page whose prose and example disagree, or for a page that describes the reference's behavior (which is most of them). "Interpretation" covers ambiguity; nothing covers contradiction.

**Does it land?** Yes, on the framing; partially on the substance. The substance, "argue every departure from the reference in writing, citing the docs", is a real discipline and better than any other port's. But the claim that the documentation *is* the authority is false as stated; the precedence order that actually governs is: documentation where it clearly speaks > incorporated authority over its own domain (except when the value model disagrees, row 2) > the package's value model > the reference. Write that down and the concept becomes coherent.

### (2) Host-native value model

**Steelman.** JSON itself has no number model (RFC 8259 only promises interoperability for doubles). The reference's binary64 is not "JSONata's number", it is JavaScript's. A Go program already holds `int64`s; forcing them through binary64 loses identifiers silently, which is the worst outcome for a transform over API payloads. Letting the host's values be the values means zero serialization, zero copying, and no lossy conversion at the boundary; and the class rules 4, 5, 8 keep it honest.

**The attack.** The value model in `jsonata.go` is not Go's. Go's `int64 + int64` wraps; this package promotes to `*big.Int`. Go's `/` on integers truncates; this package yields `0.5`. Go's `strings.ToUpper("straße")` is `"STRAßE"` (verified above); this package promises `"STRASSE"`, which needs `x/text/cases` or a hand-rolled table. Go's `encoding/json` renders a nil map as `null`; this package renders it as `{}`. Go's `%` on a negative gives `-1` where JavaScript also gives `-1`, fine, but that is the only place the host genuinely decided. The README's own analogy says "how case folds: those are the host's"; the package overrides the host's case folding on day one. So what is actually shipping is a *designed* numeric and string tower implemented with host types. That is fine, even good, but "the host defines what a number is" is a slogan, not what happened, and rule 3 ("owes no more than its host offers and must not offer less") is vacuous since any host "offers" anything you can implement.

The deeper problem is the use case. This language exists to move values between systems, and the transform is document-supplied and evaluated by whichever client opened the document. "No parity between members ... where the models differ, the members differ, and that is correct" means the same interface document yields different values in different clients, by design. The README offers "the portable core" as consolation, explicitly "an observation, not a rule". But the portable core lists `$string` and `$keys`, and the ledger's rows 1 and 7 are divergences in exactly `$string` and `$keys`. The one promise made to authors is contradicted by the ledger on its first and seventh lines.

And the value function has an internal seam. "A decimal token denotes the nearest float64, fixed when it is decoded, and that is where a decimal's precision is fixed" and, three sentences later, "a float64 whose value is integral takes part in arithmetic as that integer" and "exactness is a property of the value, not of its provenance". Put them together: the token `1e23` is declared to have its precision fixed at about 16 significant digits, and then `1e23 + 1` yields `99999999999999991611393`, asserting 23 exact digits of an input that had one. `1e300 * 1e300` yields a 601-digit integer. This is not exactness; it is precision manufactured from the accident that binary64 values are dyadic rationals. The reference's `1e23` is, on its own terms, the more honest answer (the correctly rounded result of the sum of the two denoted values). The package's answer is strictly less defensible than either "refuse" or "round once", and it comes from letting a `.` or `e` in the token decide the value, which is the provenance-dependence the same paragraph forswears.

**Does it land?** Yes. The correct statement is "the class defines a value model; members implement it with host types", and the value model needs the decode boundary to be value-based rather than lexical (see changes 1 and 2).

### (3) The regex analogy

**Steelman.** It explains, in one paragraph, why not to port: engines are native, the notation is shared, unsupported constructs are declared (RE2 refuses backreferences and nobody calls that a bug), and results are in the host's string model. Everyone who has used `regexp` gets it instantly.

**The attack.** The analogy works precisely where its premises hold and JSONata's do not. Regex notation *has* a semantics independent of any engine (regular languages, with a well-understood operational account of the extensions); RE2's syntax is a written spec. JSONata has a tutorial. Regex's "value model surface" is characters and case folding; disagreements are Unicode edge cases. JSONata's value model surface is the whole JSON value space, and the disagreements are `9007199254740993` and `$keys` order, which are not edges. Most importantly, the analogy's central virtue, "each host does its own thing", is exactly the property that is *wrong* for a transform embedded in a document that arbitrary clients evaluate. Nobody expects a Perl regex in a config file to run under RE2; OpenBindings expects a transform in an interface document to run under every SDK. The analogy is load-bearing (it is the README's entire argument for why divergence between members is "correct") and it is carrying the wrong load. The better analogies for this niche are CEL (a spec, a fixed value model with declared overflow errors, and cel-go/cel-cpp/cel-java agreeing *because the spec fixed the model*) and XPath/XQuery over XDM (a data model with `xs:integer`, `xs:decimal`, `xs:double` so hosts cannot pick). Both are "native per host" without being "host's value model".

**Does it land?** Yes, on the "host's value model" half; no, on the "native, not ported" half, which is correct and should be kept.

### (4) Declared divergence as sufficient discipline

**Steelman.** A silent difference is a bug; a declared one, pinned to the fixture it departs from with a stated authority, is a decision that can be reviewed, reversed, and detected when the fixture changes. This is more rigor than any existing port has.

**The attack.** The discipline is only as strong as the rule that says which declarations are *permitted*, and README rule 6 permits divergence "only where the value model cannot represent a reference value". Test that against the ledger: row 8 (code points) is permitted because the *documentation* says otherwise, not because of representability; rows 3, 6, 10, 11, 12, 13 are "engine" refusals, none of which is a representability failure; row 3 is "interpretation"; row 1 is "incorporated". Ten of fourteen rows are outside rule 6's grant. Either the ledger violates the README or the README does not describe the ledger. Further, the ledger's preamble defines five authority kinds, which is the right taxonomy, and the README defines none of them; the doctrine lives in the wrong file. And "engine" is doing two jobs: a value-model-forced refusal (E1008 arguably) and a pure capability limitation (the pending regex dialect, which is a *language* restriction, not a value-model one, and which rule 6 as written flatly forbids).

Also: declared divergence only covers divergence *from the suite*. The suite is a sample. Behavior the suite does not exercise (most of the numeric tower here) has no fixture to pin to; the ledger says a member adds one, good, but then the "divergence" is from a fixture the member wrote, which is a declaration of intent, not a detected difference.

**Does it land?** Yes on the rule; no on the practice. The ledger is the best part of the repository. Rewrite rule 6 to match it.

### (5) Choosing JSONata at all

**Steelman.** It is the most expressive JSON transform notation with real mindshare (Node-RED, Logic Apps, Camunda, IBM), it has lambdas and object construction, its documentation is decent, and authors will already know it. Every alternative trades expressiveness for rigor: JMESPath has a grammar and compliance suite but no arithmetic or lambdas; CEL has a spec and a fixed value model but is a predicate language first; Jsonnet has a spec and an operational semantics but is a config language with a double-only model; XPath 3.1 has everything and nobody will write it.

**The attack.** A specification whose purpose is interoperability has pinned, as its transform language, "the documentation at a commit" of a language with no specification, and this repository is the place where that decision's cost is being paid: the doc comment of `jsonata.go` is, in effect, the first draft of the missing JSONata numeric specification, written in Go doc-comment form, by the wrong party. If JSONata is the choice, the honest consequence is that OpenBindings must publish a *profile*: the value model, the decode boundary, the refusal rules, and the regex dialect, so that "conformance to the documentation" means something for numbers. Right now, at the OpenBindings level, `$.id * 1` for an id above 2^53 is implementation-defined, and the README says so with pride.

**Does it land?** Partially. The choice is defensible on expressiveness; the *framing* ("conformance is to the documentation, no implementation privileged, nothing required about values") is where the cost hides. That is an OpenBindings spec question, and I flag it rather than rule on it.

## What a PL person would want instead

Ranked by value per effort:

1. **A language-neutral, normative value-model document in `suite/`**, extracted from `jsonata.go`'s "Numbers", "Strings, bytes, and regular expressions", and "Objects and member order" sections: the value function, the domains (integer, decimal, string, bytes, object, array, absent, null), the operation tables, the decode rule, the refusal rules. Members conform to *it*; the Go doc cites it. Nearly free: the text exists. Without it the future TS member reverse-engineers the model from Go comments and "the project's members aligning with each other" is unverifiable.
2. **One decimal policy** (single correct rounding of the exact mathematical result into float64; non-finite is D1001), deleting E1008 and settling ledger rows 3 and 6. Small change, large coherence gain.
3. **A value-based decode boundary**: a numeric token or literal denotes its mathematical value; integral values are integers however spelled. Small change; removes the `9007199254740993.0 ≠ 9007199254740993` and `1e23 + 1` warts at their source.
4. **An explicit authority precedence** in the README, including the currently unstated "reference behavior is adopted where the documentation is silent and the value model is not implicated, and that adoption is not a divergence", plus a rule for documentation self-contradiction (specific normative sentence over example; example over silence).
5. **Executable laws in the shared suite**: property tests for substitutivity across representations, carriage identity, integer closure, selection/complete agreement on success, `Marshal(Eval) ≡ EvalMarshal`. Medium effort; turns the README's rules into something a member can fail.
6. **Differential testing between members** pinned to fixtures, feeding the ledger. Medium effort.
7. **An operational semantics for JSONata's core** (sequences, paths, grouping, closures). Very high effort, and the only thing that would make "documentation as authority" literally true; lowest value per effort, so last.
8. **An OpenBindings-level profile** pinning the numeric model and regex dialect for transforms. High value, but a spec decision outside this repository.

## Semantic commitments in the API and the ledger

I state each law, then test it against the text with a concrete case.

**L1. Substitutivity of equal values.** If `a = b` then `f(a) = f(b)` for every operation the text calls value-observing.
- `1e23` (float64) vs `99999999999999991611392` (`*big.Int`): equal; `$string` gives the same digits; `+ 1` gives the same integer. Holds.
- `json.Number("1.0")` vs `int64(1)`: equal; `$string` gives `"1"` for both. Holds. But `Marshal` renders `json.Number` "as its token" (`1.0`) and float64 "as `$string` renders it" (`1`): `Marshal` is representation-observing for `json.Number` and value-observing for `float32`/`float64`. Internally inconsistent; `$string({"a": $.a})` and `Marshal(Eval("{'a': $.a}"))` disagree on the same object. Declared nowhere.
- `[]byte` under a non-injective `BytesEncoding`: `b1 ≠ b2` by bytes but `$string(b1) = $string(b2)`. Fails. The `BytesEncoding` contract does not require injectivity; it must ("for an injective encoding such as base64 that agrees" is an observation where a requirement is needed).
- `$base64encode(b)` "encodes the bytes themselves, not their presentation": a representation-observing operation on a value the text says "is a string for every purpose that observes its content". Contradiction inside one paragraph. Bytes are a third string-like domain with two representation-observing operations (`$base64encode`, and equality-without-encoding); say so.
- `$keys` on `map[string]any{"b":1,"a":2}` vs `*Object` with the same members: equal objects, different `$keys`. Fails by declaration (order is representation). Acceptable, but the partition must be enumerated exhaustively and it is not: `$string`, `$keys`, `$each`, `$spread`, `$merge`, `$sift`, construction, transform are listed; `Marshal`'s `json.Number` token, `$base64encode` of bytes, and `Reads`/`Plan` (which observe the input's *type*, `ReasonArrayInput`) are not.

**L2. Exactness of carriage.** `Eval("$", x)` returns `x` by identity; a selected member is returned by identity.
- Holds for admitted values as written; a `json.RawMessage` is carried as itself by `$` but `$.a` yields a fresh decode each read; equal by value, distinct by identity. Declared.
- The decode boundary is not exact for exponent tokens: the text `1e23` denotes 10^23 (RFC 8259 numerals are decimal); `Unmarshal` yields the float64 99999999999999991611392; `Marshal` prints that. Rule 4's "same numeric value" holds only relative to the post-decode value, and the decode changed the value. Rule 8's "unrepresentable values are failures, never silently rounded" is violated at decode by design (`9007199254740993.0` rounds silently to `...992`). Rule 8 must be scoped to integers and non-finite results, or the decode rule must change (change 1).

**L3. Closure of integer operations.** `+`, `-`, `*` over integers yield integers within `MaxIntegerBits`; `/` yields an integer or a float64; `%` is Go's `%`; `$sum`, `$abs`, `$floor`, `$ceil`, `$round(x,0)`, `$power(int, n≥0)` stay integral; integral float64 results re-enter the integer domain ("sticky integers"). Holds. `-9223372036854775808 / -1` promotes to `*big.Int`; `... % -1` is 0. Holds. Corollary the text does not state: the decimal domain is *not* closed (`0.5 * 4` is the integer 2), which is what makes `x / 100.0` behave as `x / 100`.

**L4. One rounding policy in the decimal domain.** Not claimed; the text says "two rather than one", which is a confession. Test: `9007199254740993 / 2` succeeds (round once, `4503599627370496`); `9007199254740993 * 0.5`, the same mathematical value, is E1008. `x / 1e9` succeeds while `x * 1e-9` fails. The refusal keys on the *syntactic class of an operand* (integral vs. not), not on information loss: the division loses the same digits and is permitted. The doc's rationale, "where an identifier would lose digits on entering the decimal domain", does not survive `1758000000000000123 / 1000000` yielding `1758000000000.0002`, which has already destroyed the identifier and is permitted. Grouping test: `(1e300 * 1e300) * 1.5` is E1008; `1e300 * (1e300 * 1.5)` is D1001; `1e300 * 1e300 * 1e300` succeeds with a 900-digit integer. Three outcomes, three error classes, one mathematical product.

**L5. Selection is unobservable (README rule 9).** `{"a": $error("x"), "b": 1}`: `Complete` fails; `Select("b")` under a selective plan returns 1. Fails. The doc comment states the correct, conditional law ("When Complete would succeed within the budget, Select returns the same field") and adds that budget exhaustion point and `ctx.Err()` memoization are plan- and concurrency-dependent. The README overstates; adopt the doc's wording. Also, `ReasonArrayInput`'s stated reason ("each field's value is evaluated over the whole input") does not establish non-selectability; the actual reason is that an object constructor over an *empty* array yields `{}` so field presence depends on input cardinality. Say the real reason.

**L6. The environment is closed (README rule 7).** A `Resolver` whose view's `Get(key)` consults host state is a host function keyed by an expression-chosen string; `Bindings{"env": lookup{}}` gives `$env.HOME`. Rule 7 is a policy on the caller ("implement it as an allowlist"), not a property of the class. The doc comment is honest ("see Resolver for what that door means"); the README is not. Also, "Get and Range must agree on membership; the engine trusts both" and "Resolve must return an equal view" (equal how?) are undefined-behavior clauses; a language runtime should at least promise bounded UB: no panic, within budget, result unspecified.

**L7. Divergence permission (README rule 6).** Permits only value-model representability. Ledger rows 1 (incorporated), 3 (interpretation), 8 (documentation), and 6, 10, 11, 12, 13, 14 (engine) all fall outside it. The README's own thesis (documentation over reference) is not a permitted ground under its own rule 6.

**L8. Documentation wins where it speaks.** Ledger row 2 overrides `JSON.stringify` on a binary64 value. Fails. The ledger's justification is circular ("these values are integers here" because the value function says so).

**L9. The portable core agrees everywhere.** `$string` and `$keys` are in the core and are ledger rows 1 and 7. Fails on its face.

**L10. `Reads` is sound when `known`.** Expression `$`: reads no member, reports `([], true)`; a caller who "fetches only those members" evaluates over `{}` and gets `{}`. Fails. Bare `$` or `$$` outside a member path (as an argument to `$string`, `$merge`, `$count`, or as the whole result) must make `known` false; the list names `$$` only "inside a function".

**L11. Equality is an equivalence and ordering is total over admitted values.** `[]byte = []byte` needs no encoding; `[]byte < []byte` needs one and is E1001 without it: the same `Env` supports `=` and refuses `<` on the same values. Under a non-injective encoding, `a ≠ b` with neither `a < b` nor `b < a`: a preorder, not a total order. Requiring injectivity restores totality.

**L12. Error codes are raised only where the reference defines them.** "A float64 that is not finite is an error (D1001)" on *reading* an input: the reference raises D1001 on arithmetic results, not on carrying a NaN it was handed. Minor, but the text's own rule is stricter than its practice. `Marshal` of NaN: unstated code. E1001 conflates "supply a Resolver", "your input is corrupt", "supply a BytesEncoding", and "your expression returned a closure": `Class` is defined as "what a caller can do about them" and these are four different things. E1006 codes two *policy* refusals (duplicate names, lone surrogate escapes, both syntactically legal JSON) as "malformed"; the ledger itself calls them "a binding decision this member's decoder makes", which by the README's own layering belongs to the binding, not the evaluator, and should be configurable or declared as the decoder's binding stance rather than as evaluator divergences.

**L13. Unstated language claims in the doc comment.** "`??` falls through on absent only" is a claim about the language, placed in a paragraph about bindings, with no citation and no ledger row; if the pinned documentation's operator page says null also falls through, this is a silent divergence. "`$fromMillis` ... truncated toward zero as the reference does", "`$replace` ... `$12` with one group is group 1 followed by `2`" are reference adoptions in documentation silence, which the README's split has no category for.

**L14. `$round` is "interpretation, pending".** Under the package's own value function the literal `2.675` denotes 2.67499999999999982236431605997495353221893310546875 (verified above), which is not a tie; half-to-even has nothing to decide; the answer is 2.67 and the authority is *value model*, not interpretation. The pending status contemplates rounding on the shortest spelling, which is still a function of the float64 value, so it would not violate substitutivity, but it would be a second, unnecessary, spelling-based value function. Close it.

**L15. `MaxIntegerBits` "bounds the magnitude"** but is "enforced on a token's digit count before it is parsed": digits are a proxy for bits, so either some in-range values are refused or some out-of-range tokens are parsed then refused. Say "bounds the digit count" or parse then check.

**L16. Case mapping.** "Full, locale-independent Unicode case mapping" is not Go's; Go's stdlib gives `"STRAßE"`. Either declare the dependency (`x/text/cases`) or declare the simple mapping. Under the README's regex analogy, case folding is explicitly "the host's"; this is the first place the analogy is contradicted by the package that cites it.

## What I would change

1. **Decode by value, not by spelling** (`jsonata.go` "Numbers", `Unmarshal`, `json.Number`, literals). Replace "a decimal token or literal denotes the nearest float64, fixed when it is decoded or first read" with: *"A numeric token, literal, or `json.Number` denotes its mathematical value. When that value is an integer (`1`, `1.0`, `1e23`, `9007199254740993.0`) it is an integer, int64 when it fits and `*big.Int` otherwise; when it is not, it is the nearest float64, and that is where a decimal's precision is fixed."* Then ledger row 4 becomes `1e23 + 1` is `100000000000000000000001`, which is at least the number the text said, and `Unmarshal("[9007199254740993, 9007199254740993.0]")` yields two equal values. This is the change that makes "exactness is a property of the value, not of its provenance" true.

2. **One decimal policy; delete `CodeInexact`/`ErrInexact`.** Replace the two-policy paragraph with: *"An operation with a decimal operand, and an integer division whose quotient is not an integer, yields the exact mathematical result rounded once to the nearest float64; a rounding that is not finite is D1001. Integer with integer for `+`, `-`, `*`, and exact `/` is exact."* Resolve ledger rows 3 and 6 (`$round(2.675, 2)` is 2.67, authority: value model; mixed arithmetic beyond 2^53 rounds once, authority: value model). If the project insists on refusing, then refuse *consistently*: refuse every operation whose exact result is not representable in the result domain, including `9007199254740993 / 2`, and accept that it kills the language; the current middle is the worst of both.

3. **Rewrite README rules 3, 6, 7, 8, 9 to what the code guarantees, and add the missing precedence.** Rule 3: *"It implements the class value model (`suite/value-model.md`) with its host's types."* Rule 6: *"A departure from the reference suite is permitted on one of five declared grounds: documentation, incorporated authority over its own domain, interpretation, value model, engine refusal; each is recorded with its ground and pinned to the fixture it departs from. Where the documentation is silent and the value model is not implicated, the reference's behavior is adopted and is not a divergence."* Rule 7: add *"through the caller's Resolver, which is the caller's to keep closed."* Rule 8: *"Integer overflow, non-finite results, exhausted budgets, and values the model cannot hold are failures; decimals are float64 and round as float64 does."* Rule 9: adopt the doc's conditional wording. And fix "the portable core": either remove `$string` and `$keys` or say "agree for integral numbers and for objects without integer-like keys".

4. **Extract the value model into `suite/value-model.md`** as the normative, language-neutral text the members implement (value function, domains, operation table, decode rule, bytes, order, refusal table), and have `jsonata.go`'s "# Numbers" and "# Objects and member order" cite it. Same content, right owner; it is what makes the TS member's future alignment checkable and it is what "the class defines" actually means.

5. **Three contract fixes in `jsonata.go`.** (a) `Reads`: add *"a reference to the whole root (`$` or `$$`) anywhere but as the head of a member path makes known false."* (b) `BytesEncoding`: *"EncodeToString must be injective: distinct byte slices must encode to distinct strings; equality, ordering, and `$string` of bytes are consistent only under that condition."* (c) Split E1001 by caller action: `CodeForeignValue` (no Resolver or unresolvable), `CodeInvalidString` (not UTF-8), `CodeBytesEncoding` (bytes with no encoding), `CodeFunctionResult`; and move duplicate-member and lone-surrogate refusal out of `CodeMalformedInput` into a declared decoder stance (or a `Limits`/decoder option), since the ledger already concedes they are binding decisions.

## On the concept

The idea worth keeping is smaller than the README's framing and more valuable: *write down the semantics the reference never wrote down, implement them natively, and argue every departure in public.* The doc comment in `jsonata.go` is the best specification of JSONata's numeric behavior in existence, and the ledger is the first place anyone has separated "the documentation says", "an incorporated authority says", "we chose a reading", "our model differs", and "we refuse". That taxonomy is correct. The README does not use it; the README tells a simpler story (documentation versus host) that its own ledger contradicts in the first, second, and seventh rows, that its own doc comments contradict on case mapping and nil collections, and that its rule 6 forbids. The concept as *stated* is not coherent. The concept as *practiced* is nearly coherent and needs its doctrine rewritten to match its practice.

The two places where the practice is itself wrong are both at the number boundary, and both come from the same mistake: letting the spelling of a token decide its value and then swearing that values are independent of provenance. The consequences (`9007199254740993.0 ≠ 9007199254740993`, `1e23 + 1` manufacturing seven digits, `x / 2` permitted and `x * 0.5` refused for one mathematical result, the same product landing in three error classes by association) are not edge cases of floating point; they are artifacts of a value function that was defined in two contradictory sentences. Decode by value and round once, and the numeric model becomes something a PL person would sign: integers exact, decimals binary64, one boundary, one rounding rule, one refusal rule for the unrepresentable.

The regex analogy should be demoted to what it is good for (native, not ported; declared unsupported constructs) and stripped of the claim it is currently making (that members of an interoperability project are correct to disagree). For a document-embedded transform language the right posture is CEL's or XDM's: the *class* fixes the value model and every member implements it. This repository is already ninety percent of the way to being that class; it just insists on calling the model "the host's" when it is, demonstrably, its own. Own it, publish it in `suite/`, and then "no implementation is privileged" finally means something, because there will be a text, other than a Go doc comment, for an implementation to be conformant to.
