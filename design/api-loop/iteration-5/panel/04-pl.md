## Attacking the concept

### 1. Documentation as authority

**Steelman.** The JSONata documentation is a user manual: worked examples, function signatures, a few paragraphs on sequences and flattening. It has no grammar (the package's `ClassSyntax` and every S code are therefore reference-defined by necessity; no document tells you whether `a.b[0]` and `a.b [0]` are the same expression, what a backtick name may contain, or how `/regex/` lexes), no error catalogue (the package admits this at `Code`: "the reference's table is the catalogue"), no type lattice, no statement of what a number is, and it incorporates ECMAScript by reference at the worst possible place (`$string` is defined by `JSON.stringify`, which is defined over IEEE binary64 by ECMA-262). Membership rule 1 then says conformance is *verified against the reference test suite*, which is the reference implementation's behavior serialized. So the operational authority is "reference suite, minus ledger entries," which is exactly what every other port does, plus a ledger. The README's sentence "This is not how JSONata has been implemented elsewhere" describes a difference in policy for conflict resolution and in honesty, not a different authority.

**Does it land?** Mostly. The claim is coherent as a *precedence rule* (documentation beats reference where they conflict) and incoherent as a *definition of the language* (the documentation does not define enough to be one). The ledger itself proves this: it needed five authority categories (documentation, incorporated, interpretation, value model, engine) where the README offers two. Silence, ambiguity, and incorporation each got their own row type because the README's model could not absorb them. The fix is not to abandon the stance; it is to write down the precedence order the ledger already uses and to admit that syntax and error codes are reference-defined.

### 2. Host-native value model

**Steelman.** "The host defines what a number is" is an abdication when the language's whole purpose is moving values between systems, because it makes the meaning of a document depend on which SDK evaluated it. The README concedes this outright ("No parity between members ... that is correct") and then hedges ("aligning with each other is a quality commitment of the project"). Worse, the model here is not Go's. Go has no int64-to-big.Int promotion, no integer-plus-float addition, no "integral float64 is an integer" rule, and no ordered map. This package defines a numeric tower (int64 ∪ *big.Int ∪ float64 with exact promotion, a fraction domain fixed at binary64, and a refusal code) and an object type (`*Object`) that Go does not have. Membership rule 3, "owes no more than its host offers," bounds nothing: Go also offers `big.Rat` and `big.Float`, so binary64-for-fractions is a design choice among host offerings, not a consequence of the host.

**Does it land?** Yes on the framing, no on the substance. The value model is *designed*, and it is a reasonably good design. Calling it "the host's" hides the design decisions behind an appeal to nature and, critically, prevents the class from stating the model once so that a second member could implement the same tower. The honest statement is: "the project's value model, realized over host representations." Once stated that way, the parity question has an answer (members implement the same abstract model; representations differ), and rule 5's "by value across every representation" becomes checkable.

### 3. The regex analogy

**Steelman.** Regular expressions have a mathematical semantics (regular languages) and, in every dialect that matters, a formal syntax spec (POSIX, ECMA-262 §22.2, RE2's syntax document). Engines differ at the edges (code units versus code points, backreferences) precisely because the core meaning is fixed. JSONata has no such core. And regex engines compute a boolean and some spans; they never define an arithmetic. The analogy therefore says nothing about the part of this design that is hard.

**Does it land?** Half. On strings it is load-bearing and even helpful: Go `regexp` matching code points while JS matches UTF-16 units is exactly the shape of ledger rows 8 and 9, and nobody calls Go's engine wrong. On values-by-reference it is load-bearing. On authority and on numbers it is decorative: `regexp` documents its own syntax precisely (RE2 syntax) rather than deferring to a manual, and it has no analog to the numeric tower. Keep the analogy for what it explains; do not let it stand in for a semantics.

### 4. Declared divergence as sufficient discipline

**Steelman.** A ledger pinned to fixtures declares only what a fixture exercises; the doc comment already describes divergences no row records (integer-over-integer division beyond 2^53 yields a differently rounded value than the reference; `$string(1e23)` yields 23 digits; `$number` of a big-integer string is unspecified). It has no stability contract (is changing a row a breaking change of the Go module?). And the reader who most needs it, a document author writing transforms for an OpenBindings interface, will never open a Go package's `DIVERGENCES.md`; the OpenBindings spec says no implementation is privileged, so that author has no single place to learn what their transform does.

**Does it land?** Partially. Ledgers are necessary and this one is unusually honest. They are not sufficient: the discipline needs a class-level statement of the portable semantics (what every member must agree on), a versioning rule for the ledger, and a rule for undeclared divergences discovered later (bug or declaration?).

### 5. Choosing JSONata at all

**Steelman.** JMESPath has a specification and a compliance suite and native engines in a dozen languages; CEL has a spec and a Go-native reference; JSONPath is RFC 9535. Each already *is* the thing this README describes wanting. The "portable core" the README observes in practice (literals, bindings, conditionals, `$lookup`, `$keys`, `$merge`, `$sift`, `$string`, `$type`, `$$`) is roughly JMESPath's expressiveness. The project is paying the cost of writing a spec for someone else's language in order to use ten functions.

**Does it land?** As a critique of the record, yes; as a critique of the outcome, no. Object construction with grouping, `?:`, lambdas, and the sequence model are genuinely useful for shaping API payloads, and the OpenBindings spec has already pinned the language. What is missing is the acknowledgment, somewhere durable, that this choice buys expressiveness at the price of owning a semantics, and that the "portable core" is the part that could have been JMESPath.

## What a PL person would want instead

Ranked by value per effort:

1. **A class-level semantic core, one document, under `suite/`.** State the value domain (JSON values ∪ absent ∪ functions), the value function for numbers as a total function from representations to a mathematical domain (integers exact; non-integers as binary64, fixed at decode), the observable operations, the three rounding boundaries (decode: nearest binary64; operand: never inexact; result: exact then round once), member order as representation not value, and the authority precedence the ledger already uses (documentation > incorporated authority > this core > reference suite). Half a day of writing; it turns most of my findings below into stated laws instead of latent contradictions.
2. **Re-adjudicate the reference fixtures into a class-owned suite.** Each fixture carries an expected result and a tag: `documentation`, `reference-only`, `value-model`. Members run the suite; a `reference-only` fixture is one the class does not owe. This is what `suite/` promises; make the tags the ledger's primary key instead of free text.
3. **Executable laws as property tests**, listed in section 4 below: substitutivity of `=`, carriage identity, integer closure, `Select` ≡ `Complete` on success, `Unmarshal ∘ Marshal` on decoded input, `$number ∘ $string` on numbers.
4. **A grammar for 2.1** (PEG or EBNF) pinned in the class, because S codes cannot be documentation-conformant without one. Two to three days; every member needs it anyway.
5. **A formal operational semantics.** High effort; low marginal value once 1 through 4 exist.

## Semantic commitments in the API and the ledger

I state each law, then test it against the text.

**Law A (value function is total and single-valued).** Every admitted representation denotes exactly one value; equality is equality of values. The doc commits to this ("Every admitted numeric representation denotes one numeric value").
- *Holds* for int64/big.Int/float64/json.Number cross-comparison as stated.
- *Fails at the decode boundary in a way the README hides.* `json.Number("9007199254740993.0")` denotes, per JSON, 9007199254740993; the package assigns it 9007199254740992 ("that is where a decimal's precision is fixed"). README rule 5 promises "mathematical or textual value"; the member delivers "nearest binary64 of the token if it has a fraction or exponent." That is a defensible value function, but it must be stated as the value function, not as an exception to "mathematical value." Concrete: `9007199254740993.0 > 9007199254740992` is false here and mathematically true.
- *Fails for carriage versus observation of the same datum.* `Marshal` writes `json.Number` "as its token"; `$string` and `$string` of a containing object write the value. So `$` over `json.Number("9007199254740993.0")` marshals as `9007199254740993.0` while `$string($)` is `"9007199254740992"` and `$ + 0` marshals as `9007199254740992`. Two JSON renderings of one object by the same package disagree. Intended (carriage-faithful versus value-faithful), but state it as such.

**Law B (exactness of carriage).** A selected, copied, or rearranged value is returned with the same identity. Holds for maps, slices, scalars, and `*Object`. *Does not hold* for `json.RawMessage`: "decoded as JSON on each read," so `[$.a, $.a]` over a RawMessage root yields two distinct decodes; identity differs. Say so at the RawMessage sentence.

**Law C (closure of integer operations).** Integer op integer yields an exact integer for `+ - *`, `$sum`, `$abs`, `$floor`, `$ceil`, `$round(x, 0)`, `$power(int, nonneg int)`, with promotion to `*big.Int`. Holds as stated, bounded by `MaxIntegerBits`. Two consequences the text should own:
- `1e300 * 1e300` is a 2000-bit exact integer here and D1001 in the reference; multiplication overflow is not a ledger row (row 6 covers `$power` only), and the failure mode above 4096 bits is `CodeBudget`, which reads as resource exhaustion, not overflow. README rule 8 calls overflow a "failure"; the package makes it a Limits knob.
- `9007199254740993 - 9007199254740992` is 1 here and 0 in the reference; row 4 covers it only by the phrase "binary64 throughout." Fine, but then row 4 should also name integer division: `9007199254740993 / 3` is the exact integer `3002399751580331` here and a float in the reference.

**Law D (the rounding principle).** The doc states it: "an operand is never converted inexactly, while a non-integral result of exact operands is rounded once." Test it:
- `9007199254740993 + 0.5`: both operands are exact (0.5 is an exact binary64). The exact result is 9007199254740993.5, non-integral. By the stated principle it should round once to 9007199254740994. The package instead refuses with `E1008`. **The refusal contradicts the package's own principle.** IEEE addition is itself "exact result, rounded once"; extending that uniformly across the tower (compute in exact rationals, keep integral results exact, round non-integral results once) removes `E1008`, removes the `x / 1e9` versus `x * 1e-9` asymmetry, and makes `/` non-special. If instead the authors want refusal, then `/` must refuse inexact quotients too. The current text takes both positions.
- `9007199254740993 / 2`: exact quotient 4503599627370496.5, rounded once to the float64 4503599627370496, which is integral and therefore, by the "integral float64 is an integer" rule, an exact integer. **A rounded result now masquerades as exact**, so `$string(9007199254740993 / 2)` prints `4503599627370496` with no signal that anything was lost, while `9007199254740993 + 0.5` refuses. The model cannot both treat integrality as exactness and round results into the integral range without this. Either tag rounded results (costly, and changes the value model) or state the law honestly: "exactness is a property of representation, not provenance; a rounded float64 that is integral is thereafter an exact integer."

**Law E (comparison never rounds).** "9007199254740993 > 9007199254740992.5" is offered as the example of exact integer-versus-decimal comparison. The literal `9007199254740992.5` has an exponent-free fraction and becomes the nearest float64, which is 9007199254740992 (ulp is 2 at 2^53), an integral value and therefore an integer in this model. The comparison is integer-versus-integer; the sentence's own example does not exercise the rule it illustrates. Replace with a decimal below 2^52, e.g. `9007199254740993 > 4503599627370496.5`, or say plainly that a decimal above 2^52 cannot be non-integral in this model.

**Law F (substitutivity of equal values).** If `a = b` then every observing operation agrees on `a` and `b`. Holds for numbers by construction of the value function (checked: `1e23` as float64 and `99999999999999991611393` as `*big.Int` agree under `$string`, `$type`, arithmetic). **Fails for objects:** `x` = input `map[string]any{"b":1,"a":2}`, `y` = constructed `{"b":1,"a":2}`. `x = y` is true; `$keys(x)` is `["a","b"]`, `$keys(y)` is `["b","a"]`; `$string(x)` ≠ `$string(y)`. The doc's own sentence "Only carriage preserves a value's representation" is false: `$keys`, `$each`, `$spread`, `$string`, `$merge`, `$sift`, and the transform operator observe representation (map versus `*Object`) without carriage. README rule 5 says never by host type; this is by host type. The reference has the same non-law (JS deep-equal ignores key order), so the fix is a precise statement, not a behavior change: "member order is representation; equality ignores it; order-observing operations observe it; a map's order is sorted, an `*Object`'s is insertion."

**Law G (absence).** Absent ≠ null; `present` carries it; bindings cannot be absent; `??` falls through on absent only. Consistent throughout, including `NoInput`. One gap: `Select` of a key not in the constructor and a field whose subexpression is absent are both "absent," and the doc says `Expression.Fields` disambiguates before evaluation. Fine. But `Evaluation.Select` "descending into an array yields absent" while JSONata's own `items.0` over an array is a lookup that yields absent too; consistent, good.

**Law H (selection is unobservable).** README rule 9 is unconditional. The doc conditions it: "When Complete would succeed, Select returns the same field," and then enumerates observable differences on failure (sibling `$error` does not fail a selection; concurrent selections exhaust the budget at a different point; a selection may succeed where `Complete` exhausts `MaxWork`). Rule 9 needs the condition and a budget carve-out written into the class, not only into the member. Two further gaps:
- **Purity granularity is stated both ways.** The Selective-evaluation section says selection is available when "the selected field's subexpression is pure" (per field); `Expression.Fields` requires "fields are all pure" and `Plan` carries one `Reason` for the whole plan with `ReasonOpaque`/`ReasonUnsupportedCall` described as "a field's subexpression calls ..." (any impure field disqualifies the plan). Pick one. Plan-level is simpler and matches the `Plan` type.
- **Resolver determinism is not required.** `ObjectView` states "Get and Range must agree on membership; the engine trusts both." No such obligation is stated for `Resolver.Resolve`, yet the engine "does not memoize," calls it a different number of times under selection than under `Complete`, and rule 9 depends on it returning equal views each time. Add: "Resolve must be a pure function of `v`'s identity for the life of the evaluation."
- **A field that failed with `ctx.Err()`:** budget errors poison, `CodeInternal` closes, language errors leave siblings selectable, but nothing says whether the cancelled field itself is retryable on a later `Select`. Specify.

**Law I (bytes are strings when observed).** "Two []byte values are equal by their bytes, which agrees with equality of their encodings" (true only for injective encodings, which base64 is; say "injective" or restrict to base64). Ambiguity: equality "observes content," and observing content without a `BytesEncoding` is `E1001`; yet equality is defined by bytes without reference to the encoding. Does `a = b` on two `[]byte` with no encoding succeed or refuse? The text supports both readings. Also `$length(bytes)` is the length of the *encoding*, not the byte count; a reader will not expect that from "a []byte is a string." State it.

**Law J (nil is uniform).** "Every nil pointer, including a nil *Object, is null" versus "a nil map[string]T is the empty object" versus the `Object` type doc "a nil *Object reads as empty (Len 0 ...)." One datum, three meanings depending on whether it is evaluated or method-called, and the two unset-object representations (nil map, nil `*Object`) disagree. Make nil `*Object` the empty object; the stated rationale for nil slices and maps applies verbatim.

**Admission is not structural.** `[]any{MyStruct{}}` is an admitted container with a foreign element (resolved per element); `[]MyStruct` is foreign as a whole (the Resolver receives the slice). `[16]byte` (a UUID) is foreign because arrays are not in the admitted list at all. Not wrong, but a Resolver author has to learn it from a footgun; say it.

**Ledger consistency with the README.** README rule 6: a divergence "is permitted only where the value model cannot represent a reference value." Test each row against that:
- Rows 1 and 7 (documentation, incorporated): the value model can represent the reference value; the docs override. Not permitted by rule 6.
- Row 3 (interpretation): the float64 is identical on every host; not a representation limit.
- Rows 9, 10 (engine: duplicate keys, ill-formed strings): Go strings can hold arbitrary bytes and a map can keep the last duplicate; the member *chooses* to refuse. Not a representation limit.
- Rows 11, 12 (engine: range cap, function result): representable; policy.
- Row 13 (regex): pending, and I believe the documentation's regular-expression section names JavaScript syntax; if so, the authority is "incorporated," not "silent." Verify before ruling; if it is incorporated, the ruling is forced toward declaring what RE2 cannot do (backreferences, lookaround) as engine refusals, not toward choosing a dialect.
Roughly ten of thirteen rows are out of policy under rule 6 as written. The README rule is wrong, not the ledger; rewrite rule 6 to enumerate the five grounds.

**Ledger consistency with itself.** Row 1 says the package applies `JSON.stringify`'s rules "over its own numbers." Row 2 says an integral value renders as digits, so `$string(1e21)` is `"1000000000000000000000"`. But `1e21` is a float64 here as in JS, and `JSON.stringify(1e21)` is `"1e+21"` by the very authority row 1 incorporates. Row 2 overrides the incorporated authority for a value that authority defines, and labels it "value model." Under the README's own precedence (documentation wins where it speaks, and it speaks via incorporation), row 1's authority forbids row 2. Either narrow row 1 to "non-integral values" and justify row 2 as a class-level override of an incorporated rule, or render integral float64 ≥ 1e21 as `JSON.stringify` does. Note `$string(1e23)` is `"99999999999999991611393"` here, 23 digits no author wrote; that case belongs in row 2 either way.

**Ledger versus doc comment on `$round`.** The ledger marks it pending and says "the stub's current text is not a declaration." The package doc states the binary reading as settled. A shipped doc comment is a declaration; align them. On the merits: `$string(2.675)` here is `"2.675"` (shortest round-trip); a user who is shown `2.675` and asks for two places under half-to-even is owed `2.68`. Coherence between the number the package *shows* and the number it *rounds* argues for rounding the shortest round-trip decimal, which is well-defined for every float64, host-independent, and removes the divergence.

**Error codes.** `CodeUnsupportedValue` covers four situations with different remedies (add a Resolver; add a BytesEncoding; fix the input text; fix the expression). `Class` is defined as grouping "by what a caller can do about them"; one code for four remedies fails that criterion. "A language code is raised only in a situation the language defines for it" is unfalsifiable when the language defines no codes; say "the reference defines."

## What I would change

1. **Rewrite README rules 6 and 8 to match the member.** Rule 6: "A departure from the reference suite is permitted on one of five grounds, each declared: the documentation says otherwise; an authority the documentation incorporates says otherwise; the documentation admits more than one reading and the class chose one; the documentation is silent and the value model decides; or the member refuses under an engine code. Each entry names its ground and is pinned to the fixture it departs from." Rule 8: "A decimal token is fixed to the model's fraction type at decode. An operand is never converted inexactly. A result of exact operands is either exact or rounded once. Nothing else is rounded, saturated, or coerced."

2. **Resolve the `E1008` contradiction one way.** Preferred: delete `CodeInexact`, compute mixed operations exactly and round once, and rewrite the Numbers paragraph: "Arithmetic is exact over the operands' values. A result that is an integer is exact, int64 when it fits and *big.Int otherwise. A result that is not an integer is rounded once to the nearest float64. An integral float64 is an integer, wherever it came from; a rounded result that lands on an integer is thereafter exact." If refusal is kept, `/` must refuse inexact quotients and the principle sentence must be rewritten to say "an operation whose exact result is not representable is refused."

3. **State member order as representation, and fix the two order-related sentences.** Replace "Only carriage preserves a value's representation" with "Only carriage preserves a value's representation, and only order-observing operations observe an object's member order, which is part of its representation and not of its value: equality ignores it." Make nil `*Object` the empty object.

4. **Fix selection's stated laws.** In README rule 9: "A field obtained by selecting is identical to the same field of a complete evaluation whenever that complete evaluation succeeds within the same budget." In the package: pick plan-level purity (one `Reason` for the plan; delete "the selected field's subexpression is pure"), add "Resolve must return equal views for the same value for the life of an Evaluation," and specify retry after `ctx.Err()`.

5. **Split `E1001` and align the two `$string` rows.** `CodeUnsupportedValue` for foreign-with-no-Resolver and unresolvable only; new codes for bytes-without-encoding, invalid text, and a function-valued result. In the ledger, narrow row 1 to non-integral values and either justify row 2 as a class override of `JSON.stringify` (adding `1e23`) or drop it. Ship the `$round` doc comment and the ledger in agreement.

## On the concept

The engineering here is stronger than the story. The numeric tower, the absence flag, the carriage rule, the views, the budgets, and the selection plan are each thought through to a level most Go libraries never reach, and the doc comments are candid about costs. What is weak is the account of *why*: the README wants to say the documentation defines the language and the host defines the values, and neither is true as stated. The documentation defines examples and a precedence rule; the grammar, the error catalogue, and half the standard library's edge behavior come from the reference and its suite. The values are not Go's; they are a designed model with exact integers, binary64 fractions, an ordered object type, and a refusal code, realized over Go representations. Both are fine things to build. Neither should be described as something found rather than chosen, because the description determines what a second member would be required to match and what a document author is entitled to expect.

The specific place the concept fails its own test is exactness. The package says "never approximates," then fixes decimals at decode, rounds quotients once, refuses mixed operations that its own principle would round, and lets a rounded quotient become an exact integer by virtue of being integral. Each of those is individually defensible; together they are four policies wearing one word. A PL reader will not accept "exact" until the three boundaries are named and the law for each is written down and tested. Once they are, `E1008` either disappears or becomes uniform, and the ledger stops needing "interpretation" as a category for a question ("what does a float64 mean?") the model should have answered up front.

The regex analogy should stay, cut down to what it earns: values by reference, engines native to hosts, edge divergences declared. It does not earn the authority claim, because regex engines document their own notation and this one defers to a manual with no grammar. The right next artifact is not more Go; it is the class-level semantic core under `suite/` that says what every member owes, in what order authorities are consulted, and which of the reference's fixtures the class actually accepts. With that document the ledger becomes a diff against a spec instead of a diff against a program, which is the thing the README was trying to say all along.
